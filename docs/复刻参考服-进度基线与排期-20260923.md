# 复刻参考服：进度基线与后续排期（2026-09-23）

目标：把这个模拟服务端做到**完全复刻参考服**。这张表回答三件事：现在到哪、还差哪些、按什么顺序补完。
每系统细节见 `docs/ROADMAP.md`（英文，按系统族展开，含各系统"Next:"），本文只管全局排期。

所以"完全复刻"的可操作定义分三层，逐系统都要过：

1. **应答层**：客户端能发出的每一个功能号 / opcode，服务端都有回包（不静默、不兜底）。
2. **字段层**：回包的号与字段和抓包一致（没抓包的必须先补抓包，或明确标注"形态自定"）。
3. **玩法层**：结算、消耗、时间、掉落等可观测行为与原服一致（数值不可知处必须自定并标「未实测」）。

## 4. 单系统标准打法（细节以 `docs/项目开发工作安排表-20260923.md` §4 的 SOP 为准）

1. 定号域：查 `artifacts/npc-dialogue-probe-tags/packet-contracts.md`（100 功能逐号↔中文），或为新系统扩一份同构表。
2. 定分层：结果号（带 `EndMessage`）与按钮号不得同帧；号若携带数值，写编码并验证反解 + 32 位上限（神明许愿已踩实）。
3. 定文本：客户端两 locale 的键是否存在；缺的先补文本再发号，否则"实现了但看不见"。
4. 定状态：一个 Concern 一张表；跨天用"行上记领域日，读到旧日当新天"，不写定时任务。
5. 写码：`Application/<功能>` 纯规则 → `Infrastructure/<功能>` store → `Game/GameClientHandler.<功能>.cs` 流程 → DI 四处装配。
6. 钉住：协议检查只钉能在取值域全域判定的不变量（0..99 命中率、编码反解、客户端原文常量），不依赖随机抽样。
7. 验收：`dotnet build -c Release`（0 警告）→ 协议门 → 容器 `up --build -d server` → **实机点一遍** → 回写文档并标注哪些仍是推断。

## 6. 风险与约束

- **抓包是唯一的时间墙**：L2 的 12 个空白系统，静态只能定到"客户端画得出来"；字段真值与顺序必须抓，抓不到就只能自定并接受与原服有差。
- 客户端文本缺键会伪装成"功能没生效"（在线奖励就是这一类），所以任何新对话先查号↔键。
- 无 Go 源码，不能"照抄参考服"；`D:\Godswar`、`D:\tmp-godswar-compare` 是本仓库旧拷贝，不是参考服。
- 仓库正在被并行修改（迁移 head 已从 `..._162` 走到 `..._165`），每次排期前先对齐工作树再动手。
- 红线：技术文档第 7 行「严格禁止增加兜底机制」不可删不可绕；docs 单文件 20KB；迁移只追加；客户端两份 locale 编码必须原样保真（zh_cn BOM+CRLF / en_us 无 BOM+LF）。

## 7. 需要你定的三件口径（决定这张表能不能往下执行）

1. **复刻范围是否包含运营侧**：充值/支付、防沉迷、正式 GM 面板、反作弊 —— 若不包含，M6 整体取消，M3 只做"免费商城"。
2. **线上抓包环境是否可用**（账号、能否连原服）：可用则 M2 起每系统一次抓包；不可用则空白系统按"客户端定形 + 自定数值"推进，文档全部标「形态未对照原服」。
3. **数值以哪个为准**：只求"能玩不报错"（可自定），还是"与原服一致"（必须抓包，进度会慢一档）。

建议顺序：先 M1（不依赖任何新证据，纯清账，且把"进度"变成可自动统计的量），M2 起步前把上面第 2 条定下来。
