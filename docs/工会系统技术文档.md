## 1. 公会窗口怎么打开

与 NPC 对话同一套机制：服务端对注册官（`Athens_049` / `Sparta_049`）回

```
10067 { npcId, 0x80, 0, "Athens_049" }     48 字节
```

`+8 = 0x80` 是**窗口类型位**（其余已知取值：0 描述、3 任务、4 商店、32 仓库、
64 奖励箱、256 教学、512 功能列表）。客户端收到后**自己**升起公会窗口，
不向服务端要任何数据；参考服实测其后只有 `10068`。

**调用方**：`GameClientHandler.NpcDialogOpen.cs` 的 `IsGuildRegistrar` 分支，
常量 `GuildRegistrarOpenFlags = 0x80`。

## 3. wire opcode 全表（反汇编取证）

### 3.1 怎么得到的

客户端主消息分派函数在 `Origin.exe` 的 `0x4ea3d0`，入口取 `[消息+6]` 作为
消息 id，然后：

```asm
0x4ea861  sub  eax, 0x2711              ; eax = opcode - 10001
0x4ea866  cmp  eax, 0xc6                ; 0..198
0x4ea86b  ja   默认
0x4ea871  movzx eax, byte ptr [eax+0x4ee900]   ; ① 字节表：opcode → 槽位号
0x4ea878  jmp  dword ptr [eax*4+0x4ee82c]      ; ② 槽位号 → case 代码
```

**两级表**：`0x4ee900` 起 199 字节把 opcode 映射到槽位，`0x4ee82c` 起 53 个
dword 把槽位映射到处理代码。每个 case 体里都有一条
`push offset "MSG_XXX"`（该字符串在整个镜像里**只被引用一次**），据此把
槽位反标成消息名。

**方法自证**：这样得到的 `10169 = MSG_SERVER_NOTE`，与仓库里独立从抓包测出的
`Opcodes.ServerNote = 10169` 完全一致；反查出的建会应答 `10137` 也正好紧邻
实测的建会请求 `10136`。

## 4. 载荷布局（反汇编取证）

约定：**body** = 包内 payload（即整包去掉 4 字节包头）。所有偏移都相对 body。

### 4.1 `10138` BASE_INFO

`SetConsortiaInfo`（`0x4a8220`，参数 `ecx = 包首`）逐字段读取：

| body 偏移 | 类型 | 客户端去向 | 取证 | 本仓库取值 |
|---|---|---|---|---|
| +0x00 | char[64] ASCIIZ | 公会名 | ✓ | `guilds.name` |
| +0x40 | u8 | 结构 +0x14C → 文案 `ConsortiaLevel` | ✓ | `guilds.level` |
| +0x44 | u32 | 结构 +0x144 → 与 `ConsortiaFunds` 同组显示 | ✓ 位置 | `guilds.gold` |
| +0x48 | u32 | 结构 +0x148 → 与 `ConsortiaBijou` 同组显示 | ✓ 位置 | 0 |
| +0x4C | u32 | 结构 +0x150（UI 里与 1 比较） | ✓ 位置 | 0 |
| +0x50 | char[64] ASCIIZ | 结构 +0x40 | ✓ 位置 | `guilds.proclamation` |
| +0x150 | f32 | 结构 +0x154 | ✓ 位置 | 0 |
| +0x154 | u32 | 结构 +0x15C → `ConsortiaFunds` | ✓ | `guilds.silver` |
| +0x158 | u32 | 结构 +0x160 → `ConsortiaBijou` | ✓ | `guilds.bijou` |
| +0x15C | u32 | 结构 +0x158 → `MemberMax` | ✓ | `guilds.member_limit` |
| +0x160 | u32 | 结构 +0x164 → 与 `ConsortiaAltarText` 同组 | ✓ 位置 | 0 |
| +0x164 | u32 | **建筑数量**（数组元素数，结构 +0x168） | ✓ 实测 | 0 |
| +0x168 | (u32,u32)[] | **建筑数组**：每项 `(建筑类型, 等级)`，等级 **1–12** | ✓ 实测 | 空 |

整包长度：`4 + 0x16C`。

**重要**：`SetConsortiaInfo` 内部会写 `[consortia+0xa34] = 1`，即**客户端的
「我在公会里」状态就是这一包设的**。所以只要把 BASE_INFO 推给客户端，G 键
窗口就有内容可画 —— 这正是此前「建会成功但 G 键里什么都没有」的原因。

#### 4.1.1 实测修正：`+0x164`/`+0x168` 是**建筑列表**，不是成员名册

2026-09-21 实测：把公会成员写成 `(角色id, 职务)` 的 8 字节数组填进
`+0x168`、数量填进 `+0x164` 后，客户端把内容显示在**建筑**栏位而不是成员处。
结论：

- 该数组 = **公会建筑列表**，每项 `(建筑类型, 等级)`，**单个建筑等级上限 12**；
- 窗口的「成员上限：N/M」里的 N **不是**由它驱动，把名册写进去不会改变 N；
- 因此 `+0x164` 计数目前**留空（0）**是正确的占位，不能在建筑系统落地前乱填。

**建筑数组的写法（实测可显示，务必照此写）**：

| 位置 | 内容 |
|---|---|
| `+0x164` | u32 = 建筑**数量 N** |
| `+0x168 + i*8` | u32 = 第 i 项 `building_type`（来自 `guild_buildings`） |
| `+0x16C + i*8` | u32 = 第 i 项 `level` |
| 整包长度 | `4 + 0x168 + N×8` |
| 等级取值域 | **1–12**（客户端建筑等级上限） |

> **2026-09-22 已修**：首版实现把成员 `(角色id, 职务)` 写进了这个数组，导致客户端
> **建筑栏显示乱码**（玩家实测"建筑出来的是乱码"）。现在 `GuildBaseInfo` /
> `GuildCreateResponse` 都改从 `guild_buildings` 读 `(building_type, level)` 写入；
> 公会没有建筑时数量为 0、数组为空 —— 窗口建筑栏不再出现任何伪造条目。
> 名册只走 `10143`。

实测：`N = 1` 时窗口建筑栏出现一条记录（该条即 2026-09-21 由成员数据写出）。
`CREATE_RESPONSE` 里同一数组位于 `+0x18C`、数量在 `+0x184`，因为它的结果字节固定在
`+0x1CC`，所以**最多容纳 8 项**。

### 4.2 `10143` MEMBER_LIST

处理体（`0x4edb5a`）读 `[包+8]` 作计数、记录从 `[包+0xc]` 起、尾部标志在
`[包+0x41c]`：

| body 偏移 | 类型 | 含义 |
|---|---|---|
| +0x00 | u32 | 未证明（写 0） |
| +0x04 | u32 | 记录条数 |
| +0x08 | 记录[20] × 52 字节 | 见下 |
| +0x418 | u8 | **整表刷新标志**：非 0 时客户端先重置公会记录的成员容器再逐条加入 | ✓ 反汇编（`0x4a8810` 取 `[+0xa24]` 后调用）；**必须写 1** |

`8 + 20×52 = 0x418`，即客户端这条消息**最多装 20 名成员**，整包 `4 + 0x419`。

> **必须写 `+0x418 = 1`（整表刷新）**。实测：该标志为 0 时，客户端把每一次下发的
> 成员逐条**追加**进成员容器 —— 登录推送 + 按 G 重推就把同一个成员显示成两条
> （而在线数只算在线的那一条，于是出现"两个我、却只显示 1/1 在线"）。

单条记录 52 字节：

| 记录内偏移 | 类型 | 含义 | 取证 |
|---|---|---|---|
| +0x00 | char[32] ASCIIZ | 名字 | ✓ |
| +0x20 | int16 | 未证明（写 0；等级在 +0x23，故此处不是等级） | |
| +0x22 | u8 | **职务**（1–6，见 `Consortia.dat`） | ✓ 双证据 |
| +0x23 | u8 | **等级**（字节，上限 200 与客户端 `PlayLv` 一致） | ✓ **实测**：写 1 → 成员表显示"1 级"（角色实为 140） |
| +0x24 | u8 | 职业 | 位置推定 |
| +0x28 | u32 | 未证明（写 0；不是金币也不是银币贡献） | |
| +0x2C | u32 | **贡献（金币）** | ✓ **实测**：写 2 → 显示在"金币贡献" |
| +0x30 | u32 | **贡献（银币）** | ✓ **实测**：写 2（角色 id 探针）→ 显示在"银币贡献" |

> **三条实测教训（务必保留）**
> 1. **`+0x23` 是等级不是在线标志**：曾把它当在线标志写 1，成员表立刻显示"1 级"。
> 2. **`+0x2C` 是金币贡献、`+0x30` 是银币贡献**：分别写入可区分的真值（2），客户端分
>    别显示在"金币贡献"和"银币贡献"列 —— 这是"用可区分真值读客户端反应"这一方法在
>    本项目里两次直接定出字段语义。
> 3. **身份探针失败**：把本机对象号写进 `+0x20`（word）、角色 id 写进 `+0x30`，属性栏
>    「公会职位」**依然为空**；且 `+0x30` 实为银币贡献。因此"客户端在成员表里认出自己"
>    这条路径**已被实验否定**，属性栏职位另有来源（见 §6）。

> 在线人数（窗口 N/M 里的 N）**不是**由这两个字节驱动，其来源仍见 §6。

**窗口上的「成员上限：N/M」里 N 是在线人数**（不是成员总数）：渲染代码
`0x54191b` 推 `MemberMax200` 文案后读 `[结构+0x324]`（在线计数）与
`[结构+0x158]`（上限）；`OnlineNum`（`0x5414fe`）读的是同一个
`[[ebp+4]+0x324]`。计数由**客户端自己**按每条成员记录的在线标志统计，
所以 `+0x23` 必须如实填 —— 全部填 0 时窗口显示 `0/上限`。

职务字段的双证据：`MEMBER_LIST`/`MEMBER_ONE` 都把记录 `+0x22` 写进成员结构
`+0x04`；而 `10151` 的取职务函数（`0x4a88a0` 一带）正是读成员结构 `+0x04`。

`10144` MEMBER_ONE 与之一致，只是单条：body+0 未证明、**body+4 是在线标志
字节**、记录同样从 body+8 开始。

### 4.3 `10137` CREATE_RESPONSE

成功分支 `_CreateConsortiaSuccess`（`0x4a8080`）读：

| body 偏移 | 类型 | 含义 |
|---|---|---|
| +0x00 | u32 | **不是结果码，是发起者的对象 id**（客户端用它在自己对象列表里找玩家对象，见 4.3.1）。服务端回显 `10136` 请求 body+0 的值（实测 `0x1448` = 5192） |
| +0x04 | char[96] ASCIIZ | 公会名（96 字节均为名字区，NUL 填充） |
| +0x64 | u8 | 等级 |
| +0x68 | u32 | 祭坛标志（同 BASE_INFO +0x4C 位） |
| +0x6C | u32 | 资金次项 |
| +0x70 | u32 | 宝石次项 |
| +0x74 | char[64] ASCIIZ | 公告 |
| +0x174 | f32 | 未证明 |
| +0x178 | u32 | 资金主项 |
| +0x17C | u32 | 宝石主项 |
| +0x180 | u32 | 成员上限 |
| +0x184 | u32 | 元素计数 |
| +0x1CC | u8 | **结果种类**，0 = 成功；1–4 为客户端自己的四种失败分支 |

整包 `4 + 0x1CD`。注意它后半段与 BASE_INFO **偏移相差 0x24**（名字区更长），
两张表不能共用同一套内部顺序。

#### 4.3.1 崩溃取证：`10137` 必须先有 `10138`（2026-09-22）

**现场**：客户端「退会 → 再建会」时闪退；建会本身在服务端已成功（库里有公会）。
崩溃转储在客户端目录：

```
D:\Godswar Origin\Dump\Error.log     Exception Time: 19:58:13 (2026-9-22)
                                     Exception code: C0000005 ACCESS_VIOLATION
                                     Fault address:  004A80DB 01:000A70DB
                                     ESI:00000000   ← 空指针
Call stack: 004A80DB ← 004DE86B ← 004C1303 ← 007BF624(主循环)
```

`0x4A80DB` = `_CreateConsortiaSuccess`（`0x4a8080`）+0x5B，正是 `10137` 成功分支的
第一条写入：

```
mov edi, ecx          ; edi = 结构体（+6 = opcode，+8 = payload ⇒ edi+4 = body−4）
mov esi, edx          ; esi = 记录指针 ← 来自下面那次查找
call 0x7b7c73         ; 分配名字缓冲
0x4a80db  mov [esi+0xa24], ebx   ← ESI=0 ⇒ 写 0xa24 ⇒ AV
```

**记录指针从哪来**（`10137` 的 case `0x4ecda3`）：

```
lea esi, [edi+4]              ; esi = body−4
mov ecx, [esi+4]              ; ecx = body+0   ← 原以为的「结果码」
push ecx
mov eax, 0x15a47f0            ; 公会管理器单例
call 0x4a6e70                 ; → 返回记录或 NULL
movzx ecx, byte [esi+0x1d0]   ; = body+0x1CC，结果种类 switch（这一项原来读对了）
jmp [ecx*4+0x4eea04]          ; 0 → call 0x4a8080
```

`0x4a6e70` 是**按 id 查列表**，不是 getter：

```
cmp [eax+0x44], 0 / je → xor eax,eax → 返回 NULL   ; 列表空 → NULL
遍历 manager+0x3c 的链表：
    eax = [node+8]                 ; 记录
    ecx = [eax+0xc] / edx = [eax+0x248]
    cmp ecx, [ebp+8]               ; ★ 与 10137 的 body+0 比较
    je  → 返回该记录
返回 NULL
```

**为什么第一次建会没崩、退会后建会才崩**：`Error.log` 自 2026-09-13 起记录完整，
今天（9-22）**只有 19:58:13 这一次** `004A80DB`，而第一次建会（同一天）没有崩溃记录。
两次唯一的差别是"退过会"：退会让**客户端销毁了自己的公会记录**，而我们的发送顺序是
`10137` → `10138`，于是 `10137` 在记录还不存在时去查它 → NULL → 写 NULL → AV。第一次
建会时记录仍在，所以 key = 0 查得到，不崩。

> 因此 `body+0 = 0` **本身没错**（第一次建会实测可用），错的是**顺序**：
> `10138`（BASE_INFO，安装/刷新记录）必须在 `10137`（CREATE_RESPONSE，往记录里写）之前。

**已实施修复**（`GameClientHandler.GuildRegistrar.SendGuildWindowAsync`）：
建会成功路径改为 **`10138` → `10137` → `10143`**。

#### 4.3.2 顺序假设被证伪 + 真正的结论（2026-09-22 20:06 / 20:13）

改成 `10138` → `10137` 后**仍然崩在同一地址**（20:06:49，`ESI=0`）。随后做了一次
"留一手"对照实验：**退会时不发 `10149` 回执**（怀疑回执破坏了客户端状态），结果：

| 观察 | 结论 |
|---|---|
| 20:13:39 仍崩在 `004A80DB`，且该会话**从未收到过 `10149`** | **`10149` 回执不是元凶**，假设证伪 |
| 同一会话里退会 **UI 不刷新**（窗口仍显示已离开的公会，再点一次提示"你不在公会"） | **`10149` 回执是必需的**，已恢复发送 |

由此得到真正的结论：

1. **只要发 `10137` 就必崩**（三次崩溃全是建会，且该字段全是 0）；
2. 因此**第一次建会（公会 1 `test`）当时根本没有发过 `10137`** —— 早先"key = 0 曾经可用"
   的所谓矛盾不存在，那只是拿一个没发过这个包的旧会话做对照；
3. `0x4a6e70` 查的是**玩家对象**（按对象 id）：`_CreateConsortiaSuccess` 把公会名写进该对象
   `+0xa24`、`SetConsortiaInfo` 置 `+0xa34 = 1`，这些字段都在玩家对象上，而不是某个独立的
   "公会记录"对象。所以 body+0 必须是**发起者的对象 id**，而 `10136` 请求 body+0 正好就是
   它（实测 `0x1448` = 5192）。

**修复（已实施）**：`10137` body+0 回显 `10136` 请求 body+0 的对象 id；
`10138` 仍先发（无害），随后 `10137`，再 `10143`。

**待验证**：第 4 次建会不再闪退。若仍崩，则对象 id 不是列表键，下一步必须找到
**谁把节点插入 `manager+0x3c` 那条链**（`0x46b870` / `0x4a6e70` 都只查不插）。

**顺带的环境坑**：`docker compose --build` 会**重建容器 → 旧日志全部丢失**；
现在每次重建前会先把 `docker logs` 落盘到 `artifacts/guild-session-*.log`。

### 4.4 `10149` EXIT（退会，2026-09-22 客户端实测）
**C → S**：在 G 窗口点「离开公会」发出，实测帧 70 字节（载荷 66）：

| 载荷偏移 | 类型 | 含义 |
|---|---|---|
| +0x00 | char[64] ASCIIZ | 名字（本次抓包 = `"test"`），尾部补 0 |
| +0x40 | 2 字节 | 全 0 |

```
[game] unknown Unknown opcode=10149 len=70
4600 A527 74657374 0000…                                    ← A527 = 10149
[game] unknown-words opcode=10149 payload=66
    +0000 74657374 ["test"] 00000000 00000000 00000000
```

> 本次抓包**区分不了**「角色名」与「公会名」——角色叫 test、公会也叫 test。
> 服务端因此**不依赖这个字段判定身份**：退会只对「发这条包的那个会话」生效，
> 会话本身已经确定了角色；名字只用于拒绝「报文里写了别人的名字」的请求
> （那属于 `10152` 的语义，其布局尚未确立）。

**S → C**：参考服没抓到（参考服从未收到过退会请求），改为从客户端二进制读取处理器
（case `0x4ed4df`）：

```
push 0x957060 / call 0x4de040      ; 打印本条 MSG 名，确认是这个 case
cmp  dword [0x1575f4c], 4          ; 协议阶段门：必须 ==4 才处理
jne  0x4ec995                      ; 否则丢弃
mov  ecx, [0x1575eac]              ; GameData 单例
lea  esi, [edi+8]                  ; ★ 只取 body+0 作为名字
mov  dword [esp+0xa00], 0xd
call 0x4a1290                      ; → bool（按名字解析成员）
test bl, bl / je 0x4ed5ec          ; 命中 / 未命中两个分支
```

结论：**该 case 只读 `body+0` 的名字**，不读公会 id、不读任何数字 id。因此服务端的
应答按**请求自身的宽度回写**（名字 + 2 字节 0，整包 `4 + 66`），这是唯一被证明
会被这个处理器接受的形状。

### 4.5 `10150` / `10151` / `10152`（公告、任命降职、移除成员，2026-09-22 实测）

三个包都是玩家在 G 窗口里点出来的，**C2S 布局与 S2C 布局互为镜像**：

## 6.9 决定：属性栏「公会职位」不再追（2026-09-22）

**结论（已查清，但决定不实现）**：人物属性面板那一行 `Positionpro` 与公会消息无关，
它是客户端某个类的**第 10 号虚方法**按「属性 id」写进 GameData 的结果：

- 虚表在 `.rdata` 的 `0x9532EC`，共 **14 项**，第 10 项 = `0x4a8a00`（对象在 `0x4a2c10` 构造）；
- 该虚方法把属性 id 落到 GameData：`0x0b→+0x2A4`(=wire 80)、`0x0f→+0x2B4`、`0x12→+0x2BC`、
  `0x13→+0x2C0`、`0x19..0x1d→+0x2CC..+0x2DC`、`0x1e..0x24→+0x2E4..+0x2FC`、
  `0x25..0x29→+0x300..+0x310`、`0x2C→+0x31C`、`0x2F→+0x328`、`0x30→+0x32C`，
  浮点类 `0x2A/0x2B/0x2D/0x2E→+0x314/0x318/0x320/0x324`（其中 `0x2E→+0x324`
  正是公会窗口「N/M」计数读的字段）；
- 面板读取换算：**GameData = wire + 0x254**。

**要收尾只差一步**：找到那条属性消息（调用者用 `mov reg,[reg2+0x28]` 取第 10 号虚方法
后再 `call reg`，不是直接 `call [reg+0x28]`），然后以「虚方法 10 + 属性 id `0x0b` + 值 = 官阶」下发。

**为什么不继续**：G 键公会窗口已经正确显示成员的**职务**（`+0x22`）、等级、贡献与在线数，
属性栏那一行只是同一信息的第二种呈现，收益远低于继续逆向的成本。本次到此为止，
上面的事实留档，将来若要做，按本节最后一段即可接续。

**已排除的路径（避免重复劳动）**：六条公会消息全部不写该字段（最大 `+0x170`）；
`PlayerDetail`(10043) 的平铺字段里没有它（偏移扫描 84/88/92/96 无反应）；
`10039`(MSG_PARAMATER) 的 220 字节静态块只被战斗算式引用；
成员记录的身份探针（`+0x20`/`+0x30`）无效且 `+0x30` 实为银币贡献。

## 7. 复现方法

`tools/` 下的脚本（需要 `capstone`，已装）：

| 脚本 | 作用 |
|---|---|
| `dump-wire-opcode-map.py` | 打印完整 opcode → 消息名对照表 |
| `resolve-guild-wire-opcodes.py` | 只列公会段 opcode |
| `dump-guild-handlers.py` | 反汇编公会对各 case 体 |
| `find-guild-field-labels.py` | 用文案字符串关联字段偏移 |
| `find-receive-path.py` | 找消息分派的调用方 |

关键地址（本机 `Origin.exe`，image base `0x400000`）：分派函数 `0x4ea3d0`、
字节表 `0x4ee900`、槽位表 `0x4ee82c`、`SetConsortiaInfo` `0x4a8220`、
`_CreateConsortiaSuccess` `0x4a8080`。
**注意**：客户端目录里的 `GodsWar.map` 与出货 exe **不是同一次编译**，其地址
（如 `SetConsortiaInfo@0x701780`）对不上，必须以 exe 内实测调用为准。
