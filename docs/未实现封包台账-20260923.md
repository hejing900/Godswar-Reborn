## 五、客户端侧「能收哪些包」现在是空白

实测的负面结论（2026-09-23，别再走弯路）：**10069 / 10070 这两个客户端必定处理的号，在 `Origin.exe` 里作为 16 位或 32 位立即数一次都没出现**；客户端数据文件里也没有号↔名字表（`Settings/Sys/dial.ini` 里的 `ItemID=10069` 是物品 id，纯巧合）；也没扫到 `sub eax, 基数` + 跳转表的形态。也就是说客户端不按号数值分发，所以"拿号去 exe 里搜 handler"这条路不通，必须先破分发机制：从帧头 `[esi+2]` 的读取点入手 + 真反汇编器（capstone），或顺着 `MSG_*` 名字串被 `push offset 0x95xxxx` 引用的位置倒查。

`Origin.exe` 里聚着 **128** 个 `MSG_*` handler 名（清单：`artifacts/protocol-coverage/client-handler-names.txt`），其中 31 个能被指针式引用扫到；名字↔号的对齐映射还没做完，所以本表**不能**判断「某包客户端是否会处理」。补法两条：① 未对齐 xref 扫描（静态，能覆盖被间接引用的名字）；② 针对具体功能抓一次包，看客户端收到后有无反应（实证）。

## 六、这张表的边界

- 状态 C 是「静态四种写法都没看到」，不等于一定没实现：若某包通过反射、字典表或运行时拼接发出，静态会漏。逐条判定前不要当结论用。已确认的一例：`10086 QuestHandInAck` 在 C 里，但实现走的是`CapturedHandInAcks` 查表 + 克隆抓包字节（`PacketBuilder.QuestFrames.cs:376`），模板里的 opcode 字节没被本工具解出来，属误报。
- 「抓包提及」是号在文档中出现的次数，只证明被讨论过，字段以文档正文帧表为准。
- A/B 只描述协议层有无，不代表玩法正确；玩法验收按`docs/项目开发工作安排表-20260923.md` §4 的 SOP 走。
