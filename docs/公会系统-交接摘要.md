## 2. 最终公式（已实测，不要再改）

```
加成 = 祭坛当前等级的基础值 × 百分比
百分比 = min(floor(供奉点数 / 50000), 20) × 7.5%     ← 每 5 万点 1 档；1 档 = 基础值 ×7.5%；20 档 = ×150%
最终属性 = 角色自身属性 + 加成
```

**以祭坛 13（物理攻击，12 级基础值 540）为例：**

| 供奉点数 | 档位 | 百分比 | 加成 |
|---|---|---|---|
| 5 万 | 1 | 7.5% | +40.5 |
| 10 万 | 2 | 15% | +81 |
| 50 万 | 10 | 75% | +405 |
| **100 万** | **20（封顶）** | **150%** | **+810** |

**三条铁律**：
1. 百分比是**乘基础值的倍数**，不是"基础值之外再加的量"（满档 = 基础值 ×150%）。
2. **供奉点数为 0 的祭坛一点都不给**；没有"建了就白送"的常驻层。祭坛等级只决定**取哪一行基础值**。
3. **每座祭坛各自记账、各自只出自己的那一个属性**（表主键 `(guild_id, character_id, building_type)`）。

### 2.1 衰减（每小时扣，4 档）

```
余额 > 80万          → 8000/小时
60万 < 余额 ≤ 80万   → 5000/小时
30万 < 余额 ≤ 60万   → 1500/小时
余额 ≤ 30万          → 600/小时
```

- **这 4 个速率是【用户指定】，不是客户端原文**。`Consortia.xml` 的 `BuildingConsume` 6 行数字
  **全文没有"衰减/每小时/消耗"任何字样**（实测各出现 0 次），旧文档把它当衰减速率是【推断·未证实】，**已废弃**；
  代码**不再读 `guild_building_consume`**。
- **边界含下界**：30万 按 1500、60万 按 5000、80万 按 8000。
- 逐小时推进，**每小时按当时余额重新取档**；扣不起一小时就归零（不为负）。
- **离线时间也算，且服务器自己扣**：`小时数 = floor(now − settled_at)`，离线多久扣多久。
  **后台循环 `GuildAltarSettlement`**（每 5 分钟一跳）把所有在线角色结算落库，
  并对点数变化的角色**重算加成 + 推状态包**；惰性结算保留兜底。
  ⚠️ **第一次真实结算尚未观测到**（交接时 5 行都还差约 20 分钟满 1 小时）。
- ⚠️ **「跨整点差值 = 速率 × 小时数」尚未实测过**（纯时间问题，不是代码问题）。

## 5. 属性加成的三条链路（**改这里最容易翻倍，务必分清**）

```
CalculatedStats        = 裸值（所有写入方都来自数据库，绝不含祭坛加成）
character.MaxHp/MaxMp  = 有效上限（裸值 + 祭坛加成 + 元素被动）← 回血/治疗/队伍血条/升级夹血都读它
CharacterStats.FromCharacter() = 裸值 + 祭坛加成 + 称号加成     ← 发属性给客户端用它
```

**加成只在后两处各加一次。** 任何"把加成再减回来"的正常化都是错的
（实测过：1500 上限减 4500 → 夹成 1）。

## 6. 本轮踩过的坑（**别重犯**）

1. **属性名用编号推** → 错了 3 次（祭坛13→伤害吸收、祭坛18→魔法防御、枚举混用两套编号）。**根治 = 按 building_type 硬编码。**
2. **公式理解错** → 曾实现成「基础值 + 50%」和「公会层白送全额」，导致虚高。**百分比是乘数；点数为 0 就不给。**
3. **上限累积** → `Apply()` 把**带加成的值**写回 `CalculatedStats`，下次当裸值再加一遍 → 上限越刷越不对。**根治 = 缓存只存裸值。**
4. **MP 上限从未接线** → `maximumMana` 原先没加 `AltarBonus.MaxMp`，祭坛 10 永远无效。已修。
5. **看官网** → `zs.176.com/gh` 域名**已死**（ENOTFOUND），别再试图抓它。
6. **日志漏打字段** → 曾因日志没打 `mp=`，误判 MP 加成，浪费大量时间。**改动涉及哪个字段，日志就打哪个字段。**
