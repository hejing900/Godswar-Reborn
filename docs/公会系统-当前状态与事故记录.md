
### 7.1 ⚠️ 本轮我自己犯的错（用户实测抓出，已修）

**错误 1 —— 属性名字全错位（最严重，连错两次）**

- **第一次**：照 `AltarSuspendConfig.lua` 的 `Effect1` 名字去反推 `Consortia.xml` 的 `worship_impact_type`
  → **祭坛 13（物理攻击）加成到了伤害吸收**、哈迪斯加成到了魔法防御。
- **第二次**（"修"的时候）：改成照"编号顺序"推 → **祭坛 18（波塞冬，客户端原文魔法攻击）加成到了魔法防御**。
  实测日志：`[guild] offering ... building=18 points=1000000` → `[guild] altar bonus ... mdef=630 matk=0`。
- **根因**：`Consortia.xml` 的 `BuildingImpact` **只给 `worship_impact_type` 编号、不给属性名**，
  所以任何「按编号命名」的表**都得靠猜**。而 `WorshipImpactType` 与 `text.lua` 的 `ASC_L0_*` 属性表
  **不是同一个编号体系**（type 4 = 物理攻击，但 `ASC_L0_4` 是 HP回复），拿哪张表对都会错。
- **用户截了客户端祭坛列表的图**，图上直接把属性写在名字里 —— **这才是唯一权威**。
- **修法（根治）**：`GuildWorshipAttributes.ForAltar(buildingType, worshipImpactType)`
  **按 `building_type` 硬编码属性名**，`worship_impact_type` **只作为一致性校验**，不符就**不发放**
  （而不是发错）。见规格书 §5 表。

**教训**：数值表只给编号、不给语义时，**去客户端 UI 找原文，不要拿另一张表反推**。
反推出来"自洽"不等于对 —— 我两次都自洽，两次都错。而**校验而不是猜**能把错误变成"不发放"，至少不会给错属性。

**错误 2 —— 公式理解错（两处）**

- **「公会层白送全额」是我编的**：无条件给全部 10 座已建祭坛全额基础值，只供奉过 1 座的人白拿所有祭坛
  （实测 `hp=600`，来自从没供奉过的阿波罗）。**用户的真实规则是：祭坛等级只决定"取哪一行基础值"，
  点数决定"给不给、给多少"；点数为 0 就一点都不给。**
- **百分比理解错**：我实现成「基础值 + 50%」，用户的意思是**乘**：满 100 万点 = 基础值 × **150%**
  （祭坛 13：540 → 810）。这是同一个 810，但两点之间每档数值完全不同（正解每 5 万点 = 基础值 ×7.5%）。

**修法**：`Resolve` 里**丢弃点数为 0 的行**（不再需要 `HasOffering` 字段，`points <= 0` 就是判据），
百分比改为 `min(floor(点数/5万),20) × 7.5%` 直接**乘**基础值。

**错误 3 —— 属性上限累积（最严重，导致用户看到 HP/MP「变小」）**

`CharacterCalculatedStatsProjectionApplier.Apply` 把**带祭坛加成的值**写回 `CalculatedStats`，
而下次刷新又把它当"基础值"再加一遍 → 每刷一次就多叠一份（用户实测 MP 上限异常、数值变小）。

**修法**：**缓存只存裸值**（`liveCharacter.CalculatedStats = persistedStats`），
加成只加在 live 的 `MaxHp`/`MaxMp` 上（那才是"有效上限"，回血/治疗/队伍条都读它）。
⚠️ 我还犯过一个反向的错：为了"防翻倍"让读取时**无条件减掉**加成 —— 但缓存本来就是裸值，于是
**多减**（1500 上限减 4500 → 夹成 1）。已删掉那个 `Remove` 方法。

**错误 4 —— MP 上限从未接线**

`maximumMana` 原先只取 `persistedStats.MaxMp`，**没加 `AltarBonus.MaxMp`** → 祭坛 10（MP上限）永远无效。
HP 上限那条本来就接了，所以只有 MP 坏。

**错误 5 —— 日志漏打关键字段**

我的 `altar bonus` 日志一开始**没打 `mp=`**，导致我误判 MP 加成、浪费大量时间。
**教训：改动涉及哪个字段，日志就必须打哪个字段。**

**方法教训（最重要）**：数值表**只给编号、不给语义**时，**去客户端 UI / 文案找原文，不要拿另一张表反推**。
反推出来"自洽"不等于对 —— 我三次都自洽、三次都错。而**校验而不是猜**能把错误变成"不发放"，
至少不会给错属性。

**教训**：**「给全额」这类规则必须问清「给谁 / 对哪些祭坛生效」**，不能默认"全公会成员 / 全部祭坛"。

**错误 3 —— 0 点数行每次读都刷 `settled_at`**（只影响写入与日志，不影响属性数值，已修）

`Settle` 在点数为 0 时走 `return (points, now)`，守卫便把「结算时间」写成 now，于是每次打开公会窗口
都写一次库、日志按秒刷（`17:41:20 → 17:41:31 → 17:41:39`）。现改为：点数为 0 就原样返回、
不推进时间；点数是扣到 0 的则停在扣完那一刻。
