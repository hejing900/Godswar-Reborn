## 1. 结论（有证据）

用户报告「仙宠泉水（10090，加寿命）以及部分其他道具买不到」。

**根因不是货架缺货，而是购买时服务端拒绝。** 用户原话确认："槽位不空，我能看到但是买不了" ——
说明客户端目录里有这一条，点购买时被服务端挡下。

两处硬证据：

### 1.1 商城和绑定金币商人的目录里**已经有**这些道具和价格

商人的货架不是数据库，而是**抓包固化的目录**：

### 1.2 缺的是**运行时物品目录**

查询 `item_template_content_publication` 指向的发布批次：

```
在:  4060 4061 4062  10000 10001 10002  10020 10021 10022  10040 10041 10042  10060 10061 10099
不在: 10090（仙宠泉水）  10003  10023  10043
```

这 4 件在客户端 `ItemBaseAttribute.xml` 里**都有定义**（已核对，不会导致客户端崩溃），
但不在已发布的物品内容批次里。购买时服务端要按物品模板落地，模板缺失 → 购买被拒。

> 判断依据：【实测·查库】发布表内容 + 【实测】抓包目录内容 + 【原文】客户端
> `ItemBaseAttribute.xml`。日志里没有 `[mall]` / `[npc-shop]` 记录，
> 说明拒绝发生在这两条日志之前，具体拒绝点**尚未取证**。

## 2. 未完成的修复（尝试过，已回退）

**做法**：把 `10090` 加入 `Infrastructure/Items/PetItemContentBaseline.ReviewedItems`，
让发布器重新发布一批包含它的目录。

**结果**：服务器**启动失败并无限重启**，报 `startup_failure` + `invalidoperationexception`，
栈帧指向 `postgresitemtemplatebaselinepublisher.validatepetitemrows`。
**已回退**，服务器恢复健康。

**机制**：`PostgresItemTemplateBaselinePublisher.PublishAsync` 读取"当前已发布批次"后，
先跑一串 `PublishedXxxAreCompleteAsync`；这些检查把**基线列表**（`PetItemContentBaseline.ItemTemplates`）
逐条与批次内容比对。基线一改，比对必然失败，而失败点在**复用分支**里而不是"走新发布"——
所以它不是"检测到变化就重新发布"，而是"检测到变化就报错"。这条路径上一轮也踩过，
见 `docs/pet-work-care-handover-20260924.md` §2。

**下次要做的**：先把 `PostgresItemTemplateBaselinePublisher.PublishAsync`（行 48–185 的复用分支）
读透，搞清楚"怎样才能合法地产出新批次"（可能需要提升 manifest 版本，或先让某个
`PublishedXxxAreCompleteAsync` 返回 false 从而落到 `PrepareV9PublicationAsync`），
再动基线。**不要再次盲目改基线试验**。

## 4. 附带发现的一个 bug（未修）

`FilterUnsupportedCatalogItems`（`CapitalNpcShops.cs:368`）过滤商品时**只把保留的记录前移、
后面清零，但没有减少帧头 +10 的条目数**（也没有缩短包长）。被过滤的 id 是
`[4064, 4177, 4515, 10059]`。这会让「声明条目数」与「实际有效记录数」不一致，
客户端列目录时可能错位。**下次一并修**（应同步递减条目数）。
