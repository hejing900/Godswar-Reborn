# NPC 功能的封包格式与应答读法（2026-09-22）

这份文档回答一个问题：**客户端发来一个包，服务器该回什么，客户端才会显示内容。**
答案全部来自客户端自己的 Lua 脚本，不含猜测；每条都能用
`Localization/zh_cn/UI/XML/NpcFun/*.lua` 里的分支原句复核。

全量对照表（100 个功能、逐号逐句）由脚本生成，放在
`artifacts/npc-dialogue-probe-tags/packet-contracts.md`（重新生成：
`python tools/ClientPacketContracts.py`）。它按功能号排序，每个功能一节。
不放本目录是因为它有 450 KB，超过 `AGENTS.md` 的 20 KB 上限。

## 一、整个 NPC 对话只有三个包

| 方向 | 包 | 长度 | 里面有什么 |
|---|---|---:|---|
| 服务器 → 客户端 | `10067` | 48 | `+4` NPC 实体 ID；`+8` 功能标记位；`+12` 功能号列表（千进制打包，最低位先）；`+16` 脚本名 |
| 客户端 → 服务器 | `10069` | 92 | `+4` NPC 实体 ID；`+8` 功能号；`+16` 功能号；`+20` 玩家点中的那个号；`+24` 之后是附加参数 |
| 服务器 → 客户端 | `10070` | 12+4N | `+4` NPC 实体 ID；`+8` 页号；`+12` 起是 N 个号，客户端**每个号画一行** |

一次完整对话：

1. 玩家点 NPC → 服务器发 `10067`，把这块牌子能做哪几件事（功能号）报给客户端；
2. 客户端选中某件事 → 发 `10069`，`+8` 里带功能号；
3. 服务器发 `10070` 回一包号 → 客户端逐号画出一行文字或一个按钮；
4. 玩家点某个按钮 → 客户端把**画这个按钮的那个号**放进 `10069` 的 `+20` 发回，页号 `+8` 全程不变；
5. 回到第 3 步，直到某个号画的是「结果」，客户端自己关窗。

关键性质：**客户端只画脚本里写了分支的号。**发一个脚本没写过的号，那个号什么都不显示，
界面静默少一行——这就是「服务器不认识这个封包 / 回了包客户端没反应」的两个方向。

## 二、怎么读对照表

每节是一张表，五列：

- **服务端发的号** —— 该功能合法应答的全集。表里没写的号一律发不出内容。
- **客户端画出什么** —— 已经换成玩家真正看到的中文（从 `UI/Base/LuaText.lua` 取的原文）。
  标了 **按钮** 的就是可点项，其余是纯文字。
- **位置** —— 脚本自己 `SetPosition` 的坐标；没写坐标的号落在窗口默认槽位阶梯上
  （技术文档 §2.11 已证明：`10070` 走 `Set_NpcFun_Text`，不重置坐标）。
- **玩家点它时客户端回什么** —— 把同一个号放回 `10069`；纯文字点不到。
- **发完这号窗口是否关闭** —— 「是」即该分支带 `EndMessage(true)`，是结果不是菜单，
  不能和按钮混在同一包里发（技术文档 §3.6 的来源）。

有些行的号写成「除以 10 余 8 的号（8, 18, 28…）」，这是**号本身带数值**：客户端把号做
算术后拼进句子。这类行会标出算式，例如
`【号里有数值：(SubID - 8)/10】`——还剩 3 次机会就发 `38`，还剩 1 次就发 `18`。

## 三、例子：点「选择波塞冬 #50-1-100」

功能号 `50`，脚本 `NpcFunLuckyGods.lua`（幸运神明 / 许愿池，`Athens_074`、`Sparta_074`）。

打开时服务器发 `10070 {NPC, 50, 100, 101, 1000}`，客户端画出：

| 号 | 画出来 | 类型 |
|---:|---|---|
| `100` | 规则说明一段 + 按钮「▽选择波塞冬」 | 文字 + 按钮 |
| `101` | 按钮「▽选择阿波罗」 | 按钮 |
| `1000` | 按钮「▽领取奖励」 | 按钮 |

玩家点「▽选择波塞冬」，客户端发 `10069 {NPC, 50, 50, 100}`。服务器收到号 `100`，
第二层能回的就是这些（全部来自脚本分支，没有一种是编出来的）：

| 发这个号 | 玩家看到 | 关窗 |
|---|---|---|
| `9, 19, 29…` | 「恭喜，他听到了你的许愿并实现了它！如果马上领取，你将获得 **N** 经验值…」+ 按钮「▽选择波塞冬」（25,135），N =（号−9）/10 | 否 |
| `8, 18, 28…` | 「运气不好，你选择错误。你今天还能许愿 **N** 次」，N =（号−8）/10 | 是 |
| `7, 17, 27…` | 「果然是个见好就收的乖孩子，这些奖励你就拿去吧。你今天还能许愿 **N** 次」 | 是 |
| `2, 12, 22…` | 「你太有才了！居然连续 7 次选中了好心情的那个神！…经验值你还是直接拿去吧…」 | 是 |
| `6, 16, 26…` | 「很抱歉，5 分钟才能选一次！请再过 **N** 分钟之后再来！」，N =（号−6）/10 | 是 |
| `104` | 「你今天的许愿次数已经用完啦，明天再来吧。」 | 是 |
| `1001` | 「必须达到 55 级以上才可以进行幸运神明许愿。」 | 是 |
| 余 `3`（3/103/203…） | 「你没有进行任何选择，当然不会有奖励啦。」 | 是 |
| `201`（或余 5） | 「很抱歉，你暂时还没有任何奖励!」／按钮「领取奖励」 | 是／否 |

也就是说：**许愿成功回 9 系列并把经验值塞进十位，回错人回 8 系列并把剩余次数塞进十位，
冷却回 6 系列塞分钟数**。等级门槛、次数用完各有自己的号。这几个号之外的一律画不出来。

本服务器目前的实现（`GameClientHandler.NpcDialogOpen.cs:684`、
`WishingPoolDialogueCatalog.cs:50`）：第一页三件按钮已经会发，点神之后固定回 `108`
（即「选择错误，你今天还能许愿 10 次」），领奖回 `201`，等级不足回 `1001`。也就是说
**只有许愿成败与经验值发放没接**——接上就是按经验值算出 `9/19/29…` 里的十位，纯服务端
玩法逻辑，不需要新封包。

## 四、还没测出来的部分

对照表给的是「能回什么」，不给「点了 A 必须回 B」。B 是玩法决定，客户端里不存在这个信息，
只能靠抓包或实机点击确认。技术文档正文里已抓包验证过的对局（许愿池 §2、决斗场、
王城服务）优先于本表；两者不冲突时本表用来扩展新功能，冲突时以抓包为准。
