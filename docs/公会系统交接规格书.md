## 3. 协议规格

### 3.1 帧与分发
- 帧：`u16 长度（含头）| u16 操作码 | 载荷`，小端。
- 客户端接收分发 `0x4ea3d0`：解码结构 **操作码在 +6、载荷从 +8**；case 拿到的 `edi+4` 即 `body−4`（脚本里 `[esi+4]` = body+0，`[esi+0x1d0]` = body+0x1CC）。

### 3.3 对话点击路径（【实测】同一会话四条样本）

```
p12=1  p16=-1 p20=-1 p24=-1     ← 点页1的 “1”
p12=1  p16=6  p20=-1 p24=-1     ← 再点页2的建筑 “6”
p12=1  p16=6  p20=4  p24=-1     ← 再点说明页的动作 “4”
p12=1  p16=6  p20=4  p24=4      ← 再点页4的 “4”
p12=2  p16=13 p20=10 p24=-1     ← 供奉神明被点
```
**`+12/+16/+20/+24` = 玩家依次点过的编号（点击路径）**；层级 = 其中 ≥0 的个数；本次点击 = 最后一个；其父页 = 前一个。
（读错成"上一页+本次点击"会导致：动作点击被当成建筑点击 → 重发建筑页 → 那串号在更深一层被当成供奉确认语 `GH2003–GH2008`。）

### 3.4 提交时的包形状与「手输数额」（【实测】2026-09-23 定案）

**数额在 `+0x38`（即日志里的 `p56`），4 字节小端。** 证据：跨 7 份 `artifacts/guild-session-*.log`，所有"提交"包（`p24=0`）里 `p28`–`p52` 全是 `-1`，**唯一被写入的玩家输入值只在 `p56`**，且数值全是手输量级：

|---|---|---|---|
| 20260922-233557 | `1,5,4` | `10` | 捐金币 |
| 20260922-234008 | `1,5,4` | `12345` | 捐金币 |
| 20260922-235037 | `1,5,4` / `1,5,5` | `1` / `123` | 捐金币 / 捐银币 |
| 20260922-235037 | `2,13,10` | `5000` | 供奉 |
| 20260923-000829 | `1,5,4` / `1,6,4` / `2,14,5` | `123` / `123` / `123` | 捐金币 / 捐金币 / 捐银币 |

- 不含数额的请求（菜单、切页、定额按钮）里 `+0x38` 一律读 `-1` → **实现上"非正数 = 玩家没输"**。
- 提交包在点击路径**末尾追加客户端的确认键 `0`**：捐金币 `1,5,4,0`、捐银币 `1,5,5,0`、供奉 `2,13,10,0`；页面动作的确认也是同一个 `0`（`1,5,1,0`）。定额按钮走同一层级但末位是定额号本身（3–6、8–24）。
- **紧随其后还会有一条同伴包**：`p24=0 p28=0`、`p56=-1`（路径再加一个 `0`）。它**不带数额**，所以"`+0x38` > 0"是区分"真提交"与这条同伴包的判据，否则会重复扣款。
- **`+16` 是路径第二个编号**（供奉提交里 = 建筑号）。所以祭坛的提交**必须在祭坛动作分支里先拦截**，否则会落到通用 `Steps` 表被当成"点了建筑 N"，回 `[200+N]` 说明页 —— 这就是修好之前"供奉后窗口空白"的原因。

**供奉加成（2026-09-23 定案，用户实测确认「现在完全对了」）**：

```
加成 = 祭坛当前等级的基础值 × 百分比
百分比 = min(floor(供奉点数 / 50000), 20) × 7.5%      ← 每 5 万点 1 档，1 档 = 基础值 ×7.5%，20 档 = ×150%
基础值 = Consortia.xml BuildingImpact 的 WorshipImpactValue（该祭坛该等级那一行）
最终属性 = 角色自身属性 + 加成
```

**逐档绝对值（用户口径「每 5 万贡献加多少」）**，以祭坛 13（物理攻击，12 级基础 540）为例：

| 供奉点数 | 档位 | 百分比 | 加成 |
|---|---|---|---|
| 5 万 | 1 | 7.5% | **+40.5** |
| 10 万 | 2 | 15% | **+81** |
| 50 万 | 10 | 75% | +405 |
| 100 万 | 20（封顶） | 150% | **+810** |

公式要点：
- **百分比是「乘基础值的倍数」，不是「在基础值之外再加的量」**：满 100 万点 = 基础值 × **150%**
  （祭坛 13 基础 540 → **810**，即用户给的例子）。
- **供奉点数为 0 的祭坛，一点都不给。** 没有"建了就白送"的常驻层 —— 祭坛等级只决定**取哪一行基础值**，
  **点数决定给不给、给多少**；点数被衰减到 0 后该祭坛停止加成，之后再供奉恢复。
  （⚠️ 我曾错误实现成「公会层 = 另外白送全额基础值」，导致虚高，已删。）
- **基础值**：`Consortia.xml` `BuildingImpact` 的 **`WorshipImpactValue`**（每座祭坛每级一个值）。
  **不是** `AltarSuspendConfig.lua` 的 `Effect*_LevelN`（实例：祭坛 13，`WorshipImpactValue` 12 级 = **540**，
  `Effect1_Level12` = 330）。
- **每座祭坛各自记账、各自出自己那一个属性**（表主键 `(guild_id, character_id, building_type)`）。
- ⚠️ **客户端文案 `GH87` 与实测口径不一致**：`GH87` 写「50000供奉可以获取50%基础值」，
  但实测口径是 **5 万点 = 7.5%**、100 万点才 150%。**以实测口径为准**（用户确认），
  `GH87` 那句当作原文留档、不要照它实现。
- 属性映射见下表。
**供奉衰减（2026-09-23 用户定案，4 档）**：

60万 < 余额 ≤ 80万   → 5000/小时
30万 < 余额 ≤ 60万   → 1500/小时
余额 ≤ 30万          → 600/小时

      **不允许再用任何编号去"推"属性名**（已实测：raw id / id+1 / id+2 三种偏移全部对不上，最好只对 2/10）。
    2. **公式理解错**：曾实现成「基础值 + 50%」和「公会层白送全额」→ 虚高。**百分比是乘数**，且**点数为 0 就不给**。
    3. **上限累积（最严重）**：`CharacterCalculatedStatsProjectionApplier.Apply` 把**带加成的值**写回 `CalculatedStats`，
       下次又当基础值再加一遍 → HP/MP 上限越刷越大或越小（实测 MP 上限异常）。
       **根治 = 缓存只存裸值**（`liveCharacter.CalculatedStats = persistedStats`），加成只加在 live 的 `MaxHp`/`MaxMp` 上。
    4. **MP 上限从未接线**：`maximumMana` 原先只取 `persistedStats.MaxMp`，没加 `AltarBonus.MaxMp` → 祭坛 10 永远无效。已修。
  - **上限链路（重要，别再改错）**：
    `CalculatedStats` = **裸值**（所有写入方都来自数据库，不含祭坛加成）；
    `character.MaxHp/MaxMp` = **有效上限**（裸值 + 祭坛加成 + 元素被动），回血/治疗/队伍血条/升级夹血全读它；
    `CharacterStats.FromCharacter()` = 裸值 + 祭坛加成 + 称号加成，发属性给客户端用它。
    **加成只在上述两处各加一次**，任何"再减回来"的正常化都是错的（会导致 1500 上限减 4500 夹成 1）。
- **缺什么**：③ 客户端悬停要的 `GameAPI:GetAltarInfo(textID)` 三值（`altar_id`/`altar_lev`/`play_lev`）—— **服务端还没有对应实现**（`Opcodes.cs` 里 `10157`/`10162` 只有常量，从没发过，所以祭坛悬停里显示不出这套加成）；④ 个人供奉等级升级（`play_lev`，消耗 `Contribute`：6,9,12,…,86）；⑤ 每座祭坛的**第二个属性**（`AltarSuspendConfig.lua` 的 `Effect2`，客户端从不标注是哪个属性 → **不许编**）。
- **精确下一步**：做 ③（悬停显示）或 ④（个人供奉等级）。③ 需要先反汇编 `10162 ALTAR_INFO` / `10157`–`10161 ELEMENT_LIST` 的布局（技术文档 §6 记「布局尚未反汇编」）。
