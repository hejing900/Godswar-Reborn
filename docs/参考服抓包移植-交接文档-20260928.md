## 2. 商店移植（SOP）

### 2.1 判定
开包 `S2C 10067` 的 `flags=4`（或 7）且随后客户端发 `10068`、服务端回 `10071` 流 → 是商店。

### 2.2 拿货架
```powershell
python tools/gen_captured_shop_catalogs.py --session <uuid> `
       --out artifacts/npc-port/<日期>-shop-catalogs.json
```
输出每个 npc 的帧数/条目数/货币字节/分类。**同货架去重**：两份流只差帧头 `+4`(npc id) 与
`+12`(余额) 即视为同一货架，共用一个常量（雅典技能商人 5285=5237 就是先例）。

### 2.3 货币怎么定
- 帧内 `+9`：`2=金币 / 3=银币 / 4=绑定金币`（运行时的 `TryGetShopCurrency(byte)`）。
- **判据**：拿货架里装备类商品的单价，去客户端 `Localization\zh_cn\Settings\Sys\ItemBaseAttribute.xml`
  对 `Money` 列。本次 1000–1005 的价格 58/129/188/246/304/363 与该列逐个相等，即按**银币**定价。
- 本次按用户要求**统一银币**：载入目录时把每帧 `+9` 改写为 `3`（其余字节不动），
  这样客户端显示银币余额、购买也扣银币；`TryGetShopCurrency(kind)` 同步给 `Silver`。
  例：`PacketBuilder.CapturedSpartaMerchantShops.cs` 的 `ApplySpartaMerchantCurrency`。

### 2.4 商品必须能买到
```powershell
python tools/check_shop_items_published.py     # 把路径换成新导出的 json，确认 missing = 0
```
缺 `item_templates` 的商品会"看得到买不到"（见 `docs/shop-purchase-unavailable-20260924.md`）。

### 2.5 生成 + 接线
```powershell
python tools/emit_sparta_merchant_shops.py     # 模板，照抄改成自己的目录/键
```
改四处（缺一处就打不开或串台）：
1. `Domain/World/Content/CapitalNpcServiceProtocol.cs`
   —— 新增 `CapitalNpcServiceKind`；`TryResolve(key, interactionId)` 加 arm；
   `IsShop` 加；`TryGetShopCurrency(service)` 加（→ Silver）。
2. `Packets/PacketBuilder.CapitalNpcShops.cs` —— `GetCapitalShopCatalogSource` 加分支。
3. `Packets/PacketBuilder.Captured<Xxx>Shops.cs` —— 新生成的目录常量 + `Apply...Currency`。
4. **若同 key 已有旧 kind 绑定，必须先删旧 arm**，否则 `CS8510 该模式不可访问`（编译不过）。

## 3. 对话移植（SOP）

### 3.1 拉整棵树
```powershell
python tools/dump_session_npc_chain.py --session <uuid> --from "<起>" --to "<止>" --out artifacts/tmp/chain.txt
python tools/dump_npc_action_words.py --session <uuid> --npc <id>     # 逐帧看 10069 的每个词
```
C2S `10069` 字段（**服务端 payload 相对帧头 -4**）：

| 帧偏移 | payload 偏移 | 含义 |
|---:|---:|---|
| +8 | +4 | 功能号（= 开包 `10067` 的功能表里那个） |
| +16 | +12 | 玩家这一手点中的号（`TryReadNpcFunctionAction` 的 `subId`） |
| +20 | +16 | 上一手那一页的号（脚本化分派里的 `selection`） |
| +24 | +20 | 在这一页上**选中的条目**（脚本化分派里的 `pageSelection`） |

### 3.2 层级判定（照这个写表）

| 层 | 客户端发什么 | 服务端读哪个字段 | 表 |
|---|---|---|---|
| 开窗页 | `pick=-1, sub=-1` | 都 < 0 | `OpeningMenu` |
| 第二层 | `pick=N, sub=-1` | `selection = N` | `Steps[N]` |
| 第三层 | `pick=1, sub=M, arg0=-1` | `selection = M` | `Steps[M]` |
| 第四层 | `pick=1, sub=M, arg0=X` | `(M, X)` | `PageSelections[M][X]` |

**撞号自查**（必做）：把每一层的号码列出来，看有没有同一号码出现在两层。
有 → 必须用 `PageSelections`（第三层应答与第四层按钮同号），否则点击会被当成上一页重发。
本次战场颁发者就是这种情况（`3001-3003`、`11763-11766`）。

### 3.3 用客户端自己的数据核对
```powershell
python tools/describe_client_npc_dialogue.py flag NPC_FLAG_SYS_WAR       # 旗标 → 脚本 → 每个 SubID 的文案/页
python tools/search_client_ui.py NF_L0_W176                              # 文案键在哪个文件
```
- 目录：客户端 `Localization\zh_cn\UI\XML\NpcFun\NpcFun.lua`（旗标→脚本分发表）、
  `UI\XML\NpcFun\NpcFun<X>.lua`（每个 SubID 的分支）、`UI\Base\LuaText.lua`（文案）。
- 编码不统一：多数是 UTF-8（带 BOM），**`NpcFunQuest.lua` 是 gb18030**。
- 客户端标签自身带层级标记（如 `#3-2-176`），可用来交叉验证层级。

### 3.4 写对话 + 注册路由
- 定义放 `Game/ScriptedNpcDialogueCatalog.*.cs`；本次新增的放
  `ScriptedNpcDialogueCatalog.CapturedSpartaDialogues.cs`。
- 注册在 `ScriptedNpcDialogueCatalog.Routing.cs`，**按 NPC 键**：
  - 同一脚本的双城 NPC（实体不同、菜单相同）→ `"Athens_073" or "Sparta_073" => ByFunction(X)`；
  - 同功能号但菜单不同 → 各自 `ByFunction(不同对话)`；
  - 只注册**抓包里确实发过的**号：没点过的号不发应答（保持"未注册即不应答"的既有语义）。
- 开窗走 `ResolveScriptedNpcDialogues`，会以 `flags=0x200` + 功能表发 `10067`；
  任务页只在"玩家正带着新手链任务且该 NPC 是交付人"时优先（`HasQuestFunctionFor`）。

## 4. 内容/对话发布版本（加 NPC 才会用到）

### 4.1 什么时候必须新版本
| 情况 | 现象 | 处理 |
|---|---|---|
| 抓包有、`npc_spawn_definitions` 没有 | 游戏里**看不到** | 新增 `NpcContentBaselineV(n+1)`（+对话 `V(m+1)`） |
| 发布有、抓包没有 | 被 `DropAbsentFromCapture` 丢掉（正常） | 不动 |
| 被代码过滤器删掉（如原 `IsSuppressedSpawn`） | 看不到 | 删过滤器 |

诊断：`python tools/report_session_npc_gaps.py --session <uuid>`（输出 [A] 抓包有未发货 /
[D] 发布但不在抓包 / [E] 抓包有但**未发布**=隐形）。

### 4.2 新增版本的步骤
1. 新 key 的 `object_id`/`interaction_id` 必须在 **V1 基线与目标库**双轴都空闲
   （`tools/report_session_npc_gaps.py` 会顺带报冲突）。
2. 写 `NpcContentBaselineV(n+1).cs`：`Concat` 新行 → 排序 → 校验唯一性 → 声明
   `AddedEntryCount/ExpectedEntryCount/ExpectedRevision`。
3. **算哈希**（不能猜）：在 `tests/Godswar.Server.ProtocolChecks/NpcContentAuthorityChecks.*.cs`
   里加一个 `Check.Equal(ExpectedRevision, revision.Sha256, ...)` 的检查，先留全 0，
   跑一次读出失败信息里的 `actual`，再回填：
   ```powershell
   dotnet run --project tests/Godswar.Server.ProtocolChecks -c Release -- "Frozen database-authoritative NPC content"
   ```
4. 对话侧同步 `NpcDialogueBaselineV(m+1)`：`ExpectedTextCount = V(m).ExpectedTextCount + 新增 NPC 数`
   （发布的文本数 = spawn 行数），`ExpectedSpawnRevision = V(n+1)`，同样实算 `ExpectedRevision`。
5. 发布器切指针：`PostgresNpcContentBaselinePublisher`（`Publisher` 常量、当前版本比较、
   `LoadDefinitions`、revision 校验、**前任列表补上 V(n)**）、
   `PostgresNpcDialogueBaselinePublisher`（同名引用全部换版本、`Publisher` 常量、
   `IsSupportedPreviousRevision` 保留旧版本）。
6. 上次实测值（供对照）：内容 `D06157C9…53E273`(407 行)、对话 `1D92379B…A59C`(texts=407/routes=36)。
