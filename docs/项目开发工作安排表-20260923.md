## 3. 分层与放置约定（新增代码写在哪）

| 层 | 目录 | 约定 |
| --- | --- | --- |
| 协议 | `Protocol/Opcodes.cs`、`Packets/PacketBuilder.*` | 一个 opcode 一处声明 + 一处构造函数 |
| 会话流程 | `Game/GameClientHandler.<功能>.cs` | 只依赖 Application 层接口，不碰 `Npgsql`；每个功能单独分部文件 |
| 规则/数值 | `Application/<功能>/` | 纯函数 + 常量，能被协议检查直接钉住（如 `LuckyGodsWishPolicy`） |
| 存储 | `Infrastructure/<功能>/` | 一个 Concern 一张表；迁移只追加不改历史 |
| 数据 | `State/DatabaseMigrations/` | 迁移 `yyyymmdd_NNN_snake_case`，NNN 递增，head 由 `--schema-metadata` 报 |
| 客户端文本 | `Localization/zh_cn` 与 `en_us` 两份 | **编码必须原样保真**：zh_cn = UTF-8 BOM+CRLF，en_us = UTF-8 无 BOM+LF；改完要完全重启客户端 |
| 工具/产物 | `tools/*.py`（可复核脚本）、`artifacts/`（生成物，不进 `docs/`） | 生成物超 20KB 一律放 `artifacts/`，`docs/` 只留读法与被指向的入口 |

## 4. 单个功能的固定流程（SOP）

1. 读客户端脚本，列出该功能号的**可回号全集**与每号画出的中文（已有生成表就查表）。
2. 判分层：哪些号是结果（带 `EndMessage`）、哪些是按钮；结果号**不得**与按钮同帧。
3. 定号域：需要携带数值的，写出 `号 = 值×10 + 尾数` 之类的编码并**验证反解**；顺手核对 32 位上限。
4. 定文本：两份 locale 里该号的键是否存在，缺的先补文本，否则"实现了但看不见"。
5. 定状态：一个 Concern 一张表；跨天用"行上记领域日、读到旧日当新天"，不写定时任务。
6. 写纯函数 policy → store → handler 分部 → DI 四处装配（字段/构造参/运行时/工厂）。
7. 加协议检查：钉住编码、边界、客户端原文常量（每日次数、冷却、等级门槛）——**能在取值域全域判定的就别依赖随机**。
8. `dotnet build -c Release`（0 警告）→ 跑门 → 容器 `up --build -d server` → **实机点一次** → 回写文档（含"未实测"标注）。

## 5. 门禁与操作纪律

- 每个功能一次闭环、一次部署、一次实机核对；不留半截实现。
- 数据库状态实验**不要用线上角色行**：为定位领奖 bug 曾手改
  `character_lucky_gods_wish.pending_experience`，以后改用一次性夹具或测试角色。
- 领奖这类"读旧值 + 清零"必须写成一条语句（CTE），拆成同连接上两条命令会在空池分支抛
  `NpgsqlOperationInProgressException` 断掉会话；`UPDATE … RETURNING` 返回的是 SET 之后的值。
- 每次交付写清三件：改了哪些文件、跑过哪些命令、哪些结论仍是推断。
