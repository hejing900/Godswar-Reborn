# 多目标任务的目标区编码（规则与落地，2026-09-24）

> 【实测·抓包】= `packet_transactions`；【原文·客户端】= `Localization/zh_cn/Text/Quest/<id>.dat`；
> 【推断】= 由 1 目标与 2 目标样本推出的通式，未实测。

本文只讲一件事：客户端靠**哪几个字节**决定任务窗口里画几个目标。改之前我们的服务端
不管任务有几个目标，客户端只画一个。

---

## 一、规则：并排 u16 数组，第 i 个目标写第 i 槽

| 帧 | 偏移 | 内容 |
|---|---|---|
| `10082`（接取应答，648 字节） | `+20` | kind：有击杀目标 = `8`，没有 = `4` |
| | `+32, +34, +36 …` | 怪物 id，**每目标一个 u16** |
| | `+48, +50, +52 …` | 所需数量，**每目标一个 u16** |
| `10076`（后续详情） | `+16` / `+28…` / `+44…` | 同上，整体前移 4 字节 |
| `10090`（登录快照，每个 96 字节描述符） | `+68` / `+40…` / `+56…` / `+80 + 4i` | kind / 怪物 / 数量 / 第 i 目标的进度 |

槽位容量【推断】：`10082` 的怪物数组 `+32` 与数量数组 `+48` 相隔 16 字节（按 u16 最多 8 槽）；
快照描述符里两个数组各只有 12 字节（`+40…+51`、`+56…+67`，`+68` 就是 kind）→ 6 槽。
代码取更紧的 **6**（`QuestObjectiveMaximumSlots`）。任务内容里最多 3 个目标。

## 二、证据

1. **我们自己的 1 目标样本**【实测】：`10090` 里 quest 1523/1531 的描述符只在
   `+40`/`+56` 第一槽有值（1013/12、1412/20），`+68` = 8。
2. **参考服的 2 目标样本**【实测】：quest **1533**（客户端文本写"消灭15个尘羽鹰身人**和**
   15个巫怒鹰身人"）的 `10082` 与 `10076` 都是 kind=8，且**前两槽都有值**：
   怪物 `+32=1414, +34=1415`、数量 `+48=20, +50=20`。
3. **数值不抄**：参考服那帧的数量是 20/20，而客户端文本与我们自己的任务数据都是 15/15。
   编码照抄，数值照我们自己的——测试里明确断言 `0F000F00`（15/15），不是 `14001400`。
4. **反例（说明"槽数 ≠ 文本目标数"）**：quest **1528** 文本是"消灭控制者威尔**和**20个
   波斯进攻者"，参考服只填了 1 槽（`1411, 1`）。填几槽是服务端决定的，不是照文本数。

## 三、三目标任务：通式直接覆盖【推断】

1 目标（我们）+ 2 目标（参考服）给出的是"第 i 个目标 → 第 i 槽"这条通式；3 目标就是
第 3 槽，没有任何新字段。**没有 3 槽的抓包样本**，全库 22 个 `10082/10076` 帧里实测最多 2 槽。

我们内容里正好有两个三目标任务，已按通式覆盖：

| 阵营 | 任务 | 目标（槽 0 / 1 / 2） |
|---|---|---|
| Sparta | 545 | Fluttering Swords(1446,30) / Animated Axes(1445,30) / Wild Spears(1447,30) |
| Athens | 1545 | Young Firemane Dragons(1428,30) / Young Flamescale Dragons(1427,30) / Young Jade Dragons(1429,30) |

## 四、覆盖范围：两个阵营 17 个多目标任务

Sparta（9）：528、533、537、539、541、545、578、589、593
Athens（8）：1533、1537、1539、1541、1545、1578、1589、1593

编码器是共用的（`StarterQuestObjectives.For(questId)` 驱动），所以一条规则同时覆盖两个阵营，
没有按阵营分叉的代码。

## 五、改了什么

| 位置 | 内容 |
|---|---|
| `Packets/PacketBuilder.QuestFrames.cs` | 新增 `WriteObjectiveSlots` / `WriteSnapshotObjectives`；`QuestAnswer`(10082)、`QuestNextDetail`(10076)、`QuestSnapshot`(10090) 三处改为按槽写 u16，不再是单个 u32/i32；`QuestSnapshotEntry` 增加可选 `Objectives`（旧的单目标三元组保持原行为，逐字节不变） |
| `Game/GameClientHandler.Quests.cs` | 快照不再只发布"当前未完成的目标"，而是把每个目标连同各自的进度一起发 |
| `tests/.../QuestObjectiveSlotChecks.cs` | 新增：1533 的两槽与抓包逐字节一致（怪物 `86058705`）、545/1545 三槽、520 单槽不变、1525 无目标保持 kind≠8、快照多槽与逐槽进度 |
| `tests/.../QuestProtocolChecks.cs` | 改掉旧的"多目标任务留空"断言：参考服自己给 1533 的就是 kind=8 + 两槽，而留空正是客户端只画一行的原因 |
| `Packets/PacketBuilder.QuestFrames.cs`（注释） | 10076 那段"参考服 79 帧全是 kind=4、builder 永不写目标"的旧结论按 9/24 抓包更正；当年的空指针故障原因（kind 与目标区只写一半）保留在注释里 |

## 六、仍未实测的两点（不编）

1. **3 槽没有样本**：通式推断，Sparta 545 / Athens 1545 实机点一次即可坐实。
2. **快照里第 2、3 个目标的进度偏移**：单目标样本把"已完成数"放在 `+80` 那个 32 位字段的
   高 16 位（3/10 记作 `3 << 16`），多目标按 `+80 + 4i` 平行推【推断】；没有多目标快照样本。

## 七、复现

```sql
SELECT to_char(captured_at AT TIME ZONE 'Asia/Shanghai','MM-DD HH24:MI:SS.MS') AS t,
       direction, opcode, encode(clear_bytes,'hex')
FROM packet_transactions
WHERE opcode IN (10082,10076,10090) AND direction='S2C' ORDER BY captured_at;
```
