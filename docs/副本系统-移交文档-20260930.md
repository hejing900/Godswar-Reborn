## 三、当前版本的已知问题（都有原始证据）

### 1. 同一个人被**重复排队进副本**（会重复扣次数）— 未修
```
[instance-entry] member join queued character=12e1 instance=c0f34aa6… reservation=19b6aa2d…
[instance-entry] member admitted        character=25 instance=c0f34aa6…
[instance-entry] member join queued character=12e1 instance=c0f34aa6… reservation=c86a42d8…
[instance-entry] member join queued character=12e1 instance=c0f34aa6… reservation=31cca020…
[instance-entry] member join queued character=12e1 instance=c0f34aa6… reservation=bf5b8a59…
```
同一人、同一副本，**没有去重**，每次排队都新建一张入场单（`reservation`）→ 人被反复拉入、次数被重复占用。

### 2. **美杜莎界面邀请不了人**：请求被判为格式错误 — 未修
```
[instance-invite] rejected malformed request character=test scene=209 name='12e1'
[instance-invite] rejected malformed request character=test scene=209 name='12v312'
```
对照成功的邀请是 `scene=224`（亚特兰蒂斯）。

**根因（已在代码中定位）——注意范围：这不是"美杜莎邀请整个坏了"。运营实测美杜莎的邀请是可用的；被丢弃的是特定情况下从 209 发出的帧。**

- 客户端 10224 现在由共用处理器接管：`Game\GameClientHandler.InstanceInvitation.cs:16-60`。
  它在 `:37-48` 做判定：`TryResolveInvitedInstance(clientSceneId, …)` 失败即打印
  `rejected malformed request` 并 `return`（丢包）。
- 场景解析表 `Domain\World\Content\InstanceCallerProtocol.cs:482-491` 只认四个场景：

  | 客户端场景 | 目标 | 常量 |
  |---|---|---|
  | 224 | 亚特兰蒂斯 | `AtlantisClientSceneId` |
  | 227 | 飘渺幻境 | `WonderlandClientSceneId` |
  | 229 / 230 | 港湾遇袭（两个等级段） | `HarborAttackFirst/SecondClientSceneId` |
  | **209（美杜莎·进阶）/ 223（美杜莎·普通）** | **未收录 → 该帧被判为格式错误丢弃** | `MedusaIslandRosterPolicy.EnhancedClientSceneId = 209`（普通 = 223） |

- 因此：**美杜莎邀请平时可用**（走它自己那条路），但**从 209 界面发出的同型邀请帧会被这个共用处理器丢弃**。
- 修法（低风险）：把 209 / 223 补进解析表，或让拒绝分支不再把它当 "malformed" 记录。
  **落地前先确认该帧出现的具体场景，不要凭单行日志下结论。**

**修法**：在 `GameClientHandler.InstanceInvitation.cs` 中把 `scene == 209` **转给美杜莎原有邀请路径**，而不是丢包；
其它已知场景保持现状，未知场景仍丢包 + 记录。
落地前需先核对美杜莎邀请入口的签名与它对帧内"邀请号"（payload `+4`）的期待，**照着它原有实现接回去，不要新写一套**。

### 3. 亚特兰蒂斯**组队发奖**：已改，**未验证** — 待测
根因（有数据库证据）：存档层只按"报名准入名单"加载成员。
证据（修复前的三条组队局）：
```
表头 character_ids = {19,25}   但成员表只有 character_id = 19
```
已改：`PostgresAtlantisCompletionRewardStore.Reads.cs` 的 `LockCharactersAsync` 改为加载「在场名单 ∪ 报名名单」；
`PostgresAtlantisCompletionRewardStore.cs` 的校验由"人数完全一致"改为"每个报名成员必须存在且身份一致"。
**部署后尚未做任何实机验证。**

### 4. 美杜莎"队长出本把队友带走"：已改，**未验证** — 待测
根因：为修"奖励发不出"曾删掉该路径的"等满 30 秒"门槛，而该路径同时负责"把所有人送出场" → 变成一进终态就把全队送走。
已改：`GameSessionRegistry.MedusaTerminationEgress.cs` 中**结算保持立刻**，**送所有人出场重新受 30 秒窗口约束**。
规则已由运营确认：**A 方案——点离开的人先走，其余人到点自动送出**。

### 5. 数据库与代码不一致（**必须记住**）
- 约束 `ck_atlantis_completion_rewards_characters_admitted`（`character_ids <@ admitted_character_ids`）**已在开发库手工删除**（当前该表 13 条约束中已不含它，可自行核对）。
- **但代码里的迁移仍会重建它** → 换新数据库、或重建库时会再次出现，组队发奖会被它挡住。
- 待办：新增一条迁移，把它删除或改成正确语义（在场名单允许包含被邀请者）。

### 6. 名单里"(队长)"后缀对所有人都显示 — 挂起
- 已确认：`+40 = 1` 渲染为「在线（客户端自动加"(队长)"）」；`2` = 等待中；`0` = 离线；其它值整行不画。
- `+42`、`+43` 试过，**对"(队长)"后缀无影响**（两次单变量实验）。
- 结论：该后缀**不由这 44 字节记录里的这两个字节决定**；要解决需要客户端反汇编或原版服务端真实帧作为证据。**未解决，勿再试字节。**

### 7. "成员 / 名单来源"仍未共用（架构债）
- `GameSessionRegistry.InstanceRoster.cs`（462 行）**内部仍按副本类型分支**取名册与"已进场"：
  飘渺 `OriginalMembers ∪ JoinedMembers`、亚特兰蒂斯 `_atlantisRunRosters`、港湾 `OriginalMembers`、美杜莎 leader 注册携带的 roster。

## 七、必须遵守的硬约束（踩过的坑）

1. **不得在持有注册表 `_gate` 时 `await` I/O** —— 曾导致组队进副本全员卡死。
2. **同一批文件不能有两个写手**（并行改会互相覆盖）。
3. **不许因为"内部记录读不到"就把成员从名单里删掉** —— 这是"队友进场后消失"的根因。
4. **名单状态字节只许发 0 / 1 / 2**（`0`=离线、`1`=在线、`2`=等待中）；其它值客户端**整行不画**。
5. **奖励只发给结算时仍在副本内的角色**；掉线不算在场；每次进本独立结算；取档一律"就低"。
6. 迁移验证只能在一次性数据库上做，**开发库只由运营授权才可改**。
