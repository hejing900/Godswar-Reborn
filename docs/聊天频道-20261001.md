## 一、原先的状态（问题）

- 全仓库只有 **一个聊天号** `Talk = 10035`（`Opcodes.cs:45`），没有队伍/公会/世界/私聊号；
- 处理只有一条路：`GameClientHandler.Dispatch.cs` 的 `case Opcodes.Talk` →
  `BroadcastToCurrentMapAsync` → `BroadcastToCurrentWorldInstanceAsync`
  （`WorldBroadcast.cs:366`）——**只发给发包人自己所在的那个 world instance**；
- 频道字段（帧内 `+8`）**从来没被读过**，所以阵营/公会/小队/世界全被拍扁成"同图喊话"。
  运营的实测：切到阵营、公会、小队各发一条，服务端日志三条**完全一样**
  （`[world] broadcast talk map=0 character=test recipients=2`），看不出任何区别。

## 二、频道表（全部来自运营实机发送，逐帧抓取）

抓取方式：服务端在 `case Opcodes.Talk` 临时打印整帧 hex（`[chat-probe]`），
运营在**同一角色**上逐个频道各发一条内容不同的消息。

| 频道 | 帧内 `+8`（频道字） | 证据（正文） |
|---|---|---|
| 小队 | `0x402` | `test:damson` |
| 公会 | `0x404` | `test:n2` |
| 阵营 | `0x408` | `test:cherry` |
| 同图 / 普通 | `0x410` | `test:appl` |
| **世界** | `0x482` | `test:appl` **与** `test:banana`（两次不同内容、同一频道字） |
| **私聊** | `0x40401` / `0x60401` | `12e1test:nihao` / `12v312test:haha` |

**帧结构**（负载相对偏移，即 4 字节长度/号头之后）：

```
+0  u32  发言者对象 id（抓到的都是 0x1448，即运营角色 test 的对象 id）
+4  u32  文本字节数（含结尾 2 字节）
+8  u32  频道字
+12      UTF-16LE 正文（客户端自己拼了"说话人名字:"）
```

**频道字是位域**（由上面五个值推出，且每一项都有帧支撑）：

```
bit1 0x02 = 小队      bit2 0x04 = 公会      bit3 0x08 = 阵营      bit4 0x10 = 同图
bit7 0x80 = 全服广播标志（世界频道打开它；世界 = 0x400 | 0x80 | 0x02 = 0x482）
bit18 0x40000 = 私聊标志（两个私聊帧都带，且低位固定为 0x401）
```

**未验证**：两个私聊帧相差 `0x20000`，其含义**未知**（已记录在代码注释里）。
实现上**不依赖**它：判定私聊只看 `0x40000` 标志 + 低位 `0x401` + 正文里带收件人名字。

**私聊的渲染格式**（运营在收件人屏幕上实测）：`test对你说:nihao`
即客户端把收到的私聊渲染成 **"〈说话人〉对你说:〈内容〉"**。

## 三、实现（全部在服务端，客户端零改动）

| 文件 | 内容 |
|---|---|
| `Domain/World/Content/ChatChannelProtocol.cs` | 频道字 → 受众的**纯函数**；帧解析；私聊正文拆分（`<收件人><说话人>:<内容>`）。**未知频道字一律退回"同图"**，绝不吞消息、也绝不发得比同图更远 |
| `Packets/PacketBuilder.Chat.cs` | 10035 帧构造（UTF-16，唯一支持中文的文本帧） |
| `Game/GameSessionRegistry.Chat.cs` | 收件人集合解析（按会话/阵营/指定角色集）+ 逐会话投递 + 按名字找在线角色 |
| `Game/GameClientHandler.Chat.cs` | 六路分派：世界 / 阵营 / 公会 / 小队 / 同图 / 私聊 |

行为要点：

1. **世界** = 本进程服务的所有在线会话（`ResolveChatRecipients`，不带过滤）；
2. **阵营** = `Character.Camp` 相同的在线会话；
3. **公会** = 从公会存储读出成员角色 id（`PostgresGuildStore.TryReadGuildAsync`），再取其中在线者；
   未入公会 → 服务端回一条提示，不广播；
4. **小队** = 队长队伍成员表；不在队伍（人数 < 2）→ 提示，不广播；
5. **同图** = **完全保持原样**（原帧原样转给同实例的人，含发包人自己），
   因为它是上线前就在跑的行为，这一轮不动它；
6. **私聊** = 正文里解析收件人名字 → 找在线会话 → 把内容重写为 `〈说话人〉:〈内容〉` 后
   只发给该角色；**本人身份一律取当前会话**，帧里自带的发言者对象 id 永不信任；
7. 除"同图"外，**发送者不会被回写**（客户端自己会显示自己发的那行，回写会显示两遍）。

## 六、待实机验收（双开）

1. 两个号在**不同地图**，A 用**世界**频道发一句 → B 应看到（这是本轮的核心修复）；
2. A 用**阵营**频道 → 同阵营的 B 看到，敌对阵营的号看不到；
3. A 用**公会**频道（先让两个号入同一公会）→ 只有同公会看到；
4. A 用**小队**频道（先组队）→ 只有队友看到；
5. A 按名字私聊 B（B 在别的地图）→ B 屏幕上应出现 `A对你说:内容`；
6. 同图"普通"频道 → 与改动前**完全一样**。

**仍然未验证 / 已知缺口**：

- 客户端对"不在视野内的发送者对象 id"如何渲染，**只有实机能回答**。若世界/阵营/公会频道
  在实机上不显示，回退方案是改用系统消息（10038）投递，但**那一路只支持 ASCII**，中文会丢——
  所以中文 + 跨图必须用 10035；
- 私聊帧里 `0x20000` 那一位的含义；"对你说"里"你"是客户端渲染还是线上传的，未取到服务端下行帧；
- 未做：发言节流（防刷屏）、屏蔽/黑名单、频道开关。
