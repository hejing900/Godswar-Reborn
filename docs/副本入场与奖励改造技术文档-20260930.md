# 副本入场流程与奖励结算改造 — 技术文档（2026-09-29 ~ 09-30）

本文记录本轮改造**实现的功能、采用的方法、踩过的坑与验证方式**。所有结论均来自本仓库代码或线上服务端日志，
未经验证的地方在文中明确标注。

---

## 一、交付的功能

### 1. 四个副本统一为"点了才进"

| 副本 | 队员弹窗 | 点击后 | 不点 | 队长进场后再点 |
|---|---|---|---|---|
| 港湾遇袭 | 与队长相同的原生"进入副本"窗口（10222 + 10216） | 进场 | 60 秒后窗口自行消失，**当日次数不扣** | 支持 |
| 亚特兰蒂斯 | 同上（共享同一段代码） | 进场 | 同上 | 支持 |
| 飘渺幻境 | 同上 | 进场 | 同上 | 支持（含运行名单补加） |
| 美杜莎 | 其原生邀请确认框（10224，带邀请人名字） | 各自领次数后进场 | 邀请超时，次数不扣 | 支持（原有机制） |

**说明（如实记录）**：美杜莎沿用它原有的邀请机制，没有替换成另外三家使用的"进入窗口"封包。四条行为
（全员弹窗 / 点了才进 / 不点消失且不扣次数 / 后加入可见进度）均满足，且它是唯一在真实客户端上早有验证的路径。

### 2. 进度面板发给每个成员（含后加入者）

面板按"**结算/展示时在副本内**"发放（`WorldReady` + 所有权有效 + 实例匹配），新成员第一次收到的是
**完整快照**（副本状态 + 成员名单 + 当前分数 + 剩余时间），不是从零开始。

### 3. 新增：输入角色名邀请进副本

客户端发出 10224（client → server），服务端为受邀者发送**与报名队友完全相同的那两帧**，
受邀者弹出同样的窗口、同样 60 秒、点击后各自领次数进场。**副本内任何成员都可以邀请**。

### 4. 奖励改为"按副本进度算一份、发给结算时仍在副本内的角色"

| 维度 | 规则 |
|---|---|
| 奖励值 / 档次 | **不变**：亚特兰蒂斯按报名队伍分类（1 人=深海猎人，2–5 人=海床探索者）、飘渺按岛屿进度、美杜莎按难度 |
| 发给谁 | **结算那一刻还在副本内**的角色（`WorldReady` + 所有权有效 + 实例匹配）；**掉线 = 不在场 = 不发** |
| 后加入者 | 持有自己的入场次数记录，**在场即享有** |
| 提前离开者 | 不享有 |
| 结算次数 | 以 `world_instance_id` 为幂等键，**每次进本独立结算**，同一次运行只发一次 |

### 5. 明确未改动

计分逻辑、怪物（刷新/AI/血量）、掉落表、每日次数上限、客户端 —— **一行未改**。

## 二、实现方法

### 2.1 逐人入场窗口的抽象

- 开关：`InstanceCallerProtocol.UsesPerMemberEntryWindow(kind)`（港湾 / 亚特兰蒂斯 / 飘渺为 true；赫拉克勒斯单人不适用）。
- 窗口记录：`MemberEntryWindow`（以**每个成员会话**为键，持有队长会话、客户端场景号、成员列表、已确认集合、目标绑定）。
  点击判定 `IsMemberEntryWindowMember` / `TryConfirmMemberEntryWindow` / `ConfirmedMemberEntryMembers`。
- 绑定：队长提交时 `BindMemberEntryRun(leader, instance, map, x, z)` 写入目标副本；成员确认时据此生成 `MemberEntryJoin`。
- 次数：**只有真正进入的角色才花掉当日次数**。未确认者走既有的
  `ReleaseLegacyInstanceDailyEntryMembersAsync` 释放路径（与旧副本"没进就不扣"一致）。

### 2.2 受邀者复用报名队友封包

服务端收到客户端 10224 后：

1. 解析（见 4.1 的封包布局）；
2. 校验：邀请人此刻在跑着的副本内（按副本类型分派判定）、受邀者在线 / 同大区 / 不在该副本内；
3. 为受邀会话登记一条**已绑定目标副本**的窗口记录（等同队长提交后的状态）；
4. 发送 `InstanceEntryQueueState(scene)` + `InstanceEntryNotice(scene)` —— 与报名队友**同一对封包**。

### 2.3 服务端主动拉人（关键设计）

被邀请/后确认的成员，**传送不由其自身封包处理发起**，而是：

```
成员点击 → 领自己的当日次数 → 飘渺先补运行名单 → 入队（TryEnqueueMemberEntryJoin）
世界 tick（AdvanceMemberEntryJoinsAsync）→ 用传送那一刻的最新会话状态构造命令
        → TransitionPartyMemberToAuthoritativeInstanceAsync（注册表 → 会话 sink）
```

即与报名队友**完全同一调用点**。原因见 4.6。

### 2.4 飘渺运行中加人（怪物不动）

- `WonderlandRunRuntime._party` 改为可写 + `TryAddLateParticipant`：**只扩参与名单**（岛屿传送、友方战斗表现、区域目标筛选），
  `_plans` 与已发布怪物**不变**；
- `MapInstance.Wonderland.MonsterRuntime.TryAddParticipant`：补进**攻击者白名单**（否则新成员伤害不结算）；
- `MapInstance.TryAppendWonderlandParticipant`：一次性扩运行名单 + 怪物攻击者名单 + 封盘名单；
- `GameSessionRegistry.TryAdmitWonderlandLateEntrant`：要求已封盘、人在副本外 → 先经世界属主追加 → 成功后写入 `Entrants`
  （传送门 `MayEnterWonderlandMap` 据此放行）。

### 2.5 奖励按在场结算

| 副本 | 改动 |
|---|---|
| 亚特兰蒂斯 | `MapInstance.AtlantisCompletionRewards.FreezeAtlantisCompletionMembers`：收件人由"在场 ∩ 报名集"改为"**在场**"；`AdmittedMembers` 仍是报名队伍（档次与持久化校验锚点）；契约放松"收件人必须属于报名队伍"；请求新增 `AdmissionReservationIds` |
| 飘渺 | `WonderlandTitleRequest` 去掉"收件人必须是报名成员"的包含校验；收件人原本就取自 `SnapshotWonderlandMembersLocked`（在场） |
| 美杜莎 | `SettleMedusaCompletionRewardAsync`：奖励名单由 `egress.AdmittedCharacterIds`（冻结）改为 `egress.Members`（在场）；**出口名单不动**，该送回主城的人照旧送回；无人在场则不结算 |

### 2.6 面板发送时机

面板状态包（`RepetitionSync` 等）必须在**客户端目标场景就绪之后**发送，否则客户端会丢弃状态，
表现为"窗口出来了但没有结束副本按钮"。亚特兰蒂斯/飘渺/美杜莎原有实现本就带就绪门槛，港湾已补齐。

## 四、踩过的坑（现象 → 根因 → 修法）

### 4.1 解析偏移写错，导致邀请者掉线

- **现象**：客户端发来 10224，邀请者立刻掉线，受邀者收不到。
- **日志**：`[game-fault] opcode=10224 name=RepetitionInvitation len=44 character=test ArgumentOutOfRangeException`
- **根因**：封包为 `[len][opcode][场景:4][邀请号:4][名字:32]`，负载里名字区起点是 **+8**，
  我写成了 `Slice(12, 32)`，而负载只有 40 字节 → 越界抛异常 → 会话被断开。
- **修法**：改为 `Slice(sizeof(int) * 2, 32)`，并显式校验 `Payload.Length == 40`。
- **附带发现**：名字区后面那些字节是**客户端未清零的残留**，解析必须**只读到 NUL 为止**。
- **教训**：处理客户端封包时，偏移要用"负载内偏移"再算一遍；越界必须**先在解析层挡住**，不能让它冒到断线层。

### 4.2 副本容量按报名人数创建 —— 本轮最大的坑

- **现象**：所有前置检查全部通过（世界存在、所有权、位置检查点、玩家状态、地点、实例），受邀者/后确认的队员**始终进不去**。
- **日志**（服务端自己给出）：`reason=instance transfer failed: Cannot transfer character between world instances: InstanceFull.`
- **根因**：`GameClientHandler.LegacyInstanceEntry.cs` 创建副本时把容量设为 `party.Members.Count`。
  1 人报名 = 只有 1 个位置，第二个人必然"副本已满"。
- **修法**：`Math.Max(party.Members.Count, PartyProtocol.MaximumMembers)`（至少满编 5 人）。
- **影响面**：亚特兰蒂斯 / 飘渺 / 港湾**共用这一处**，一处修复三家生效；
  美杜莎走 `CreatePreparedLocalWorldInstanceAsync`，本来就传 `MedusaIslandPolicy.MaximumPartySize`，**不受影响**。
- **教训**：连续多轮找不到原因时，应当**先去找"报错文本"**（服务端的拒绝原因字符串），
  而不是逐条打印自己以为相关的守卫。我在这上面浪费了最多时间。

### 4.3 飘渺组队"全员看起来掉线"（互相看不见、技能物品不可用、只能走）

- **日志**：组队进 205 有 `[map] transition complete`；组队进 207 **四分钟内一条都没有**；单人进 207 正常。
- **根因**：`AddWonderlandInstanceNpcs` 在**进图发布路径**里抢注册表 `_gate`，而世界 tick 正持该锁驱动同一个副本 →
  发布卡死 → 角色从未登记进实例世界（无视野、无世界存在 → 技能/物品被拒），而切换期间走路是放行的。
- **修法**：该注入改为**无锁**（会话表本身并发安全，运行快照查询本就不经注册表锁）。
- **教训**：进图/发布这类会 await I/O 的路径里**不得抢注册表锁**；运行状态归地图实例所有，注册表只做路由。

### 4.4 我自己的回归：仙境 NPC 注入丢了"仅在仙境运行中"判断

- **现象**：任何非仙境地图进图都会抛 `ArgumentException: NPC 5205 belongs to map 207, not map 208/205`，
  同时让仓库里 8~9 项亚特兰蒂斯/飘渺检查变红。
- **根因**：我拆函数时丢了守卫，导致仙境传送 NPC 被塞进当前地图名单。
- **修法**：恢复守卫（只在 207 且该会话有仙境运行时注入）。
- **教训**：拆分带前置条件的函数时，**前置条件必须跟着走**。

### 4.5 队员"点击没反应"——我先怀疑错了方向

- **现象**：飘渺组队，队员点"进入"无反应。
- **我当时的错误判断**：以为是承载封包选错（应该用美杜莎的邀请）。
- **实机抓包（真实回帧）**：
  `[instance-entry] 10217 character=12e1 scene=227 invitation=0 response=1 owned-window=1`
  —— 客户端**弹窗正常、回帧形状完全正确**，服务端也认出属于他的窗口。
- **真正原因**：飘渺在队长入场时已按当时人数**封盘**，`MayEnterWonderlandMap` 不再放人。
- **修法**：见 2.4（运行中加人，怪物不动）。
- **教训**：怀疑封包之前，先用一次抓包把事实钉死；**不要用推测推翻已验证的机制**。

### 4.6 在成员自己的封包处理里发起传送

- **现象**：受邀者点击后，传送被拒（前置条件全绿）。
- **根因**：该传送在成员**自己的封包处理**里发起 → 持有该会话的状态门（`_characterStateGate`），
  且用的是点击瞬间的快照；而报名队友是**服务端主动拉人**（另一处调用点 + 传送那一刻的最新状态）。
- **修法**：改为**入队 + 世界 tick 驱动**，走注册表到会话 sink 的同一调用点（见 2.3）。
- **教训**：同一件事如果已有"已验证可用的调用点"，就必须复用它；**自己另开一处调用点等于引入未知差异**。

### 4.7 重复点击同一窗口会释放次数

- **现象**：点两次时，第二次走到"已在内 → 拒绝 → 释放次数"分支。
- **修法**：改为**幂等**（已在内即视为已记录，继续入场，不释放）。
- **教训**：客户端的确认帧可能重复；入场这类操作必须幂等。

### 4.8 奖励"档次"与"收件人"被混为一谈

- **现象**：我把亚特兰蒂斯的奖励档次也算成"结算时在场人数"，导致"2 人报名、1 人在场"从队伍称号变成单人称号。
- **修法**：档次仍按**报名队伍**分类；只有**收件人**按在场。
- **教训**：规则里的"算什么"和"发给谁"必须分开建模。

### 4.9 奖励契约里的"收件人必须属于报名队伍"

- **现象**：后加入者在奖励落库时被拒。
- **修法**：亚特兰蒂斯 / 飘渺的奖励契约去掉该包含校验（收件人由在场快照决定；
  持久化校验仍逐条核对报名队伍以防伪造）。
- **教训**：把不变量写进契约时要问清楚——"谁有资格"与"谁在场"是两回事。

### 4.10 测试辅助函数默认自动替队长点确认

- **现象**：启用逐人窗口后，8 项亚特兰蒂斯/飘渺检查失败。
- **根因**：测试的 `InvokeAsync(handler, packet, confirmEntry: true)` 默认会自动替该会话确认窗口；
  成员从未确认 → 不会随之传送。
- **修法**：在共享入场辅助函数中**先让成员确认、再让队长确认**（与真实玩法一致）。
- **教训**：测试夹具的隐式行为会掩盖流程变化；改流程必须同步改夹具语义。

### 4.11 诊断本身的副作用与噪声

- 探针若调用**有副作用**的方法（例如"位置检查点持久化"），可能影响被测代码的真实结果；诊断应尽量只读。
- 临时日志要**成批清理**，否则会长期留在生产日志里。
- 当前仍需清理的临时诊断：`GameSessionRegistry.WonderlandRun.cs` 与
  `MapInstance.Wonderland.Admissions.cs` 中"拒绝原因"的详细日志。

### 4.12 其他

- 过滤运行检查（`-- 港湾遇袭` 之类）结果**不可信**：检查之间存在状态依赖，必须全量对比。
- 真实套接字集成检查（B18C2）**偶发失败**，重跑即过。
- 频繁部署会丢失容器日志上下文：定位问题时要注意"日志起点"，避免把重启后的空日志当成"没有发生"。

## 六、遗留与建议

1. **清理临时诊断日志**（两处，见 4.11）。
2. **美杜莎的邀请弹窗**沿用原生邀请框；若要求四家外观完全一致，需要把美杜莎也切到 10216 窗口
   （需评估其持久化入场链路，属独立改动）。
3. **邀请功能的协议检查**尚未补（当前依赖实机验证）。
4. 建议后续把"参加者 = 结算时在场"这一规则**收敛为共享实现**（目前三处各写一遍，语义一致但代码分散）。
