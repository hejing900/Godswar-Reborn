# 经验相关物品的实现

服务端对客户端经验类药水的实现记录。覆盖两类已落地的物品族、它们共用的机制、
数据库契约、已核实的运行状态，以及尚未实现的部分。

- **实现状态**：两族共 **14 瓶**已实现并落库（见
  [已核实的运行状态](#已核实的运行状态)）
- **通道**：普通背包物品使用路径，`C2S 10051`（`Opcodes.BreakItem`）
- **时长口径**：在线时间，下线停止计时
- **未实现**：天赋（TP）族，见 [尚未实现](#尚未实现)

## 1. 总览

经验类药水按"影响哪条经验"分族，每族再按"档位 × 时长"展开。

| 族 | 影响 | 物品数 | 通道 kind | 策略类 |
|---|---|---:|---:|---|
| 宠物经验药水 | 仅宠物经验 | 6 | `24` `Pet` | `PetExperienceBoostPolicy` |
| 经验药剂 | 人物经验 **且** 宠物经验 | 8 | `25` `PersistentExperiencePotion` | `ExperienceBoostPotionPolicy` |

两族**可叠加**：宠物经验药水只进宠物通道，经验药剂同时进人物与宠物通道，
而存储主键是 `(character_id, kind)`，所以各占一行、各自计时、加成相加。

天赋（TP）族共用同一套机制，但尚未实现。

状态号取自 `Magic.ini` 各技能的 `Status=`。这一点必须逐条核对，因为
**同族的技能号与状态号并不总是对齐**：宠物族 4752-4756 对应 513-517 是连续的，
但 `4747 → 508` 就跳出了经验药剂族的连续段。

## 3. 通道设计

### 3.1 为什么经验药剂要新建 kind

经验药剂同时影响人物与宠物经验，而现有通道都不合适：

- `Consumable`（kind `14`）是通用消耗品通道，**月光饼、激情玫瑰等共用它**。
  由于主键是 `(character_id, kind)`，放进去会与这些物品互相顶替。
- `Pet`（kind `24`）是宠物专用，`AffectsFighter` 明确排除它，放进去人物拿不到加成。

因此新建 `PersistentExperiencePotion`（kind `25`），并让它在
`ExperienceBoostKinds.AffectsFighter` 与 `AffectsPet` 中都为真、`AffectsTalent` 为假。

```csharp
public static bool AffectsFighter(int kind) => kind switch
{
    Talent or GuildTalent or Pet => false,
    _ => true                       // 25 走默认分支，计入人物
};

public static bool AffectsPet(int kind) => kind is
    Consumable or Weekend or Pet or Guild or FactionArea or BattlePass or
    PersistentExperiencePotion;     // 25 显式列入
```

`ExperienceBoostState` 与 `Application/Progression/ExperienceBoostContracts.cs`
各有一份 `ExperienceBoostKinds`，两处必须同步修改。

### 3.2 两个时长档共用 kind 25

60 分钟档（4500-4503）与 8 小时档（4506/4534/4535/4539）**共用 kind 25**，
这样同一档位的两个时长会走同一条档位规则，从而互相续时：

- 强效 60min → 强效 8h ＝ **9 小时 / +100%**
- 极效可顶替强效（高档顶替、旧时长清零）

### 3.3 叠加语义

| 生效中的加成 | 人物经验 | 宠物经验 |
|---|---:|---:|
| 宠物经验药水 +300%（kind 24） | — | +300%（×4） |
| 经验药剂 +300%（kind 25） | +300%（×4） | +300%（×4） |
| **两者同时** | **+300%（×4）** | **+600%（×7）** |

宠物合计是两条通道之和，所以是相加而非顶替；人物合计只取 kind 25，
因为 kind 24 对 `AffectsFighter` 为假。

## 4. 档位规则

两族共用同一条规则，实现在 `ExperienceBoostTierRule.Resolve`，各族的
`ResolveGrant` 负责先校验取值范围再委托给它。

| 新药水相对当前 | 结果 |
|---|---|
| **更高**档位 | 整体顶替：新加成、新状态、新时长；**旧剩余时长丢弃** |
| **相同**档位 | 续时：新时长加到剩余额度上，封顶**在线 24 小时** |
| **更低**档位 | 无效：既不降级也不延时；但叠加数仍扣 1、冷却仍走 1 秒 |

封顶常量是 `MaximumOnlineTicks = 24 * TimeSpan.TicksPerHour`。因为只有同档续时
才会触顶，所以封顶永远不会截断一次升级。

档位比较的键就是 `bonus_basis_points` 本身（`2,500 < 5,000 < 10,000 < 30,000 < 40,000`），
这也是状态读取器在同一 kind 内排序所依据的字段；`priority` 按
`bonusBasisPoints / 1_000` 派生，两者保持一致。

## 5. 请求路径

`C2S 10051` 被装备穿戴与物品使用共用，因此必须先做物品分类。

```text
GamePacket(10051)
  -> GameClientHandler.Dispatch.cs            case Opcodes.BreakItem
  -> GameClientHandler.InventoryActivation.HandleBreakItemAsync
       |-- payload.ClientOperationId 存在  -> HandleDurableBagItemActivationAsync
       |-- _session.IsSecure 且无令牌       -> 拒绝（身份降级）
       `-- 兼容分支：
             从已锁定的背包格分类物品
             AllowLegacyPlayerMutationFallback("pet_experience_boost_potion"
                                              / "experience_boost_potion")
             PetCommandOperationIdentity.RawLocalServer(...)
             -> HandleDurableBagItemActivationAsync
  -> PostgresPetDurableCommandExecutor.ExecuteBagItemActivationAsync
       |-- PetExperienceBoostPolicy.TryResolveItem
       |     `-> ApplyPetExperienceBoostPotionAsync
       |-- ExperienceBoostPotionPolicy.TryResolveItem
       |     `-> ApplyExperienceBoostPotionAsync
       `-- 其他物品 -> EquipBagItemAsync 或忽略
```

兼容分支只在显式启用的 `LocalDevelopment` raw-TCP 配置下可达：
`CanUseLegacyPlayerMutationFallback` 在 `requiresDurablePlayerCommands` 为 false 时
返回 true；secure 与生产会话无法进入。

`ExecuteWithBagConsumableCooldownAsync` 包住整个激活流程，因此两族都沿用
`BagConsumableCooldownPolicy` 中技能 4752-4765 的 1 秒冷却。

### 5.1 分类入口的两个清单

路由入口只有物品 ID，无法读取 `PropId` 之外的模板信息，所以两族各有一个
"是否为已审核物品"的判定，且都必须与策略类的 `Reviewed` 表保持同步：

- 宠物族：`GameClientHandler.InventoryActivation.IsReviewedPetExperienceBoostPotion`
- 经验药剂族：`ExperienceBoostPotionPolicy.IsReviewedItem`

### 5.2 客户端投影

物品使用后不发送任何施法帧。经验类药水是**物品而非技能**，
`BagConsumableActivation`（10051 回执）、`BagConsumableSkillCastVisual`（10040）
与 `SkillCastImpact`（10046）属于已停用的 HP/MP/银币实现，本路径不使用。

一次成功的消耗只发送：

1. 背包空格清理（`StorageItemKitBagDelete`）
2. 背包刷新（`SendKitBagRefreshAsync`）
3. 状态重发布（`SendExperienceBoostStatusAsync("pet-experience-boost-potion")`）

第三步会重新组合并下发完整的 `10167` 快照，把新状态、其倒计时以及所有其他
生效来源一并带上；30 秒一轮的状态对账会继续维护图标与倒计时。

两族共用 `PetDurableReceiptStatus.PetExperienceBoostActivated`（117）作为回执状态。

### 6.3 写入语句

两族共用同一条 UPSERT（完整语句见
[experience-boost-potions.md](experience-boost-potions.md)），
形如 `INSERT ... ON CONFLICT (character_id, kind) DO UPDATE ... WHERE
EXCLUDED.bonus_basis_points >= character_experience_modifiers.bonus_basis_points
RETURNING remaining_online_ticks`。要点：

- `WHERE` 子句让"低档无效"在 SQL 层也是原子的：落败的冲突不更新任何列，
  `RETURNING` 无行返回，执行器抛错。低档在调用前已被策略层拦下，这里是纵深防御。
- `activated_at` 与 `expires_at` 同取 `transaction_timestamp()`，保证 8 小时窗口
  与在线 tick 额度一致，即使事务中途墙上时钟跳变。
- `source` 形如 `pet-exp-potion:4756` / `enduring-exp-potion:4808`，且落在
  `varchar(64)` 内，可用于追溯。
- `remaining_online_ticks` **总是显式写入**，原因见 §7.2。

## 7. 数据库契约

表 `character_experience_modifiers`
（`database/postgres/065_experience_boosts.sql` 建表，
`068_online_progression_boost_duration.sql` 增加时长列，并镜像于
`PostgresSchemaMigrationCatalog.ProgressionIntervals.cs`）。

| 列 | 类型 | 说明 |
|---|---|---|
| `character_id` | `integer` | 主键成员 |
| `kind` | `integer` | `24` 宠物 / `25` 经验药剂；主键成员 |
| `status_id` | `integer` | 客户端图标与文字由它选择 |
| `bonus_basis_points` | `integer` | 2,500 / 5,000 / 10,000 / 30,000 / 40,000 |
| `priority` | `integer` | `bonus_basis_points / 1_000` |
| `source` | `varchar(64)` | `<族前缀>:<技能号>` |
| `activated_at` | `timestamptz` | `transaction_timestamp()` |
| `expires_at` | `timestamptz` | 窗口坐标 |
| `remaining_online_ticks` | `bigint` | **权威在线时长** |

### 7.1 约束与触发器

- `PRIMARY KEY (character_id, kind)` —— 每个通道每角色一行，这是"各占一行、
  互不干扰、相加生效"的结构基础。
- `trg_character_progression_boost_online_duration` —— `BEFORE INSERT OR UPDATE`
  触发器，**仅当新值与旧值相同时**才用 `expires_at - activated_at` 重算额度。
  执行器显式写入该列，因此绕过触发器，同档累计的总额不会被覆盖。
  这一点是"同档续时"能成立的前提，改动写入路径时必须留意。

其余约束、完整列语义与逐列说明见
[experience-boost-potions.md § Database contract](experience-boost-potions.md)。

### 7.2 在线时长如何被消耗

额度由常规的在线区间结算扣减（`ConsumeBoostOnlineTimeAsync`），
`GameSessionRegistry.Progression.cs` 在读取加成与会话结束时结算区间。
因此只有角色在世界内时时钟才走：登录、停在选角界面、掉线、重启服务端都不消耗。
这与代码库内其他限时加成一致：**没有墙上时钟模式，也没有逐行的时长类型判别列**。

### 7.3 加成如何生效

```text
basePetExperience    = MonsterRewardCatalog.ResolvePetExperience(...)
bonusBasisPoints     = ExperienceBoostState.TotalPetBonusBasisPoints
awardedPetExperience = MonsterRewardPolicySnapshot.ApplyExperienceMultipliers(
                           basePetExperience, bonusBasisPoints)
```

- `TotalPetBonusBasisPoints` 汇总所有 `AffectsPet` 为真的 kind（含 24 与 25）；
  `TotalBonusBasisPoints` 汇总人物通道（含 25，不含 24）。
- `ApplyExperienceMultipliers` 计算
  `base * (10_000 + bonus) * globalMultiplier / 100_000_000`。
- `PostgresMonsterRewardExtrasStore.MonsterDeathPetExperience.cs` 写入
  `character_pets.experience`，且**仅当宠物 `owned` + `is_carried` + `is_summoned` 时发放**；
  否则结算记录 `requested_experience = 0` 且 `pet_id` 为空。
  这是本功能最难观测的一环，见 §8.3。
- `10167` 报文 offset 300 的聚合值是**人物通道**，宠物专用加成不会进入该字段。

## 8. 已核实的运行状态

### 8.1 已落库（数据库实测）

查询 `godswar_local` 库（注意：同容器内还有 `godswar` 库，服务端不使用它）：

```sql
SELECT character_id, status_id, kind, bonus_basis_points, priority,
       source, activated_at, expires_at, remaining_online_ticks
FROM character_experience_modifiers
ORDER BY kind;
```

实测结果（数据库时间 `2026-09-21 02:31:20Z`）：

| character_id | status_id | kind | bonus_basis_points | source | 剩余在线时长 |
|---:|---:|---:|---:|---|---:|
| 2 | 517 | 24 | 30000 | `pet-exp-potion:4756` | 7.43 h |
| 2 | 506 | 25 | 10000 | `enduring-exp-potion:4808` | 8.80 h |

由该状态算出的实时倍率：

| 通道 | 计算 | 倍率 |
|---|---|---:|
| 宠物经验 | `(10000 + 30000 + 10000) / 10000` | **×5.0** |
| 人物经验 | `(10000 + 10000) / 10000` | **×2.0** |

逐项核对全部通过：双通道各占一行、档位与状态号正确、`source` 可追溯、
`expires_at - activated_at` 恰为 8 小时、额度在随在线时间递减、
`priority` 等于 `bonus_basis_points / 1000`。

### 8.2 已修复的路由缺陷

实现过程中发现并修复：`C2S 10051` 对这些物品原先会掉到
`[equip-re] BreakItem ignored: ... is not genuine equipment`，
事务从未开启，表现为**物品变黑后又被背包刷新恢复、数据库无写入**。
根因是 `GameClientHandler.InventoryActivation` 的兼容分支只放行显式列出的
宠物类物品，两族药水不在名单内。现已加入分类与原因码。

### 8.3 尚未观测到的部分

**乘法的实际发生（消费侧）尚未在游戏中观测到。** 输入侧（两行加成）已证实，
但 `monster_death_pet_experience` 表中的记录全部为
`requested_experience = 0` 且 `pet_id` 为空，原因是宠物未处于召唤状态，
且测试角色超出怪物奖励等级带（`MonsterRewardCatalog.ResolvePetExperience`
在 `policy.IsEligible` 为假时返回 0）。

补验方法：召唤宠物后打一只等级接近的怪，然后

```powershell
docker exec godswar-postgres psql -U godswar -d godswar_local -c `
  "SELECT requested_experience, pet_id, experience_before, experience_after, created_at FROM monster_death_pet_experience ORDER BY created_at DESC LIMIT 3;"
```

出现 `requested_experience > 0` 且 `pet_id` 非空即为生效，且
`experience_after - experience_before` 应等于 `requested_experience`。
要确认倍率，把 `requested_experience` 与该怪 tier 的基础值对比：
`MonsterRewardCatalog` 的算法是
`MonsterExperience[tier - 1] * CapturedNormalMonsterMultiplier`（乘数为 `4`），
该数组与 `BaseExperience` 均为 private，需直接读源码取值。

## 12. 运维备注

- **查库必须用 `godswar_local`**。同容器内还有 `godswar` 库，服务端不使用；
  该库中 `character_experience_modifiers` 恒为空，极易误判为"未落库"。
  服务端的 `GODSWAR_POSTGRES_CONNECTION_STRING` 决定实际库名。
- **物品变黑随即恢复**通常意味着服务端拒绝了这次使用并回推了背包刷新，
  应查 `docker logs godswar-server` 中的 `[equip-re] BreakItem ignored` 与
  `[status] EXP boost sync` 两行。
- **`bonus-bps=0` 不一定是异常**：该字段是人物通道聚合值，
  宠物专用加成（kind 24）本就不应进入。
- 重建与重启：
  `docker compose --profile legacy-raw build server` 然后
  `docker compose --profile legacy-raw up -d server`，
  健康检查通过后 5999（登录）与 7000（游戏）可用。
